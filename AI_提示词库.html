🎯 1. 出题官

1.1 概念理解题（由易到难）

适合学完概念后自测 耗时10 分钟出题 + 20 分钟做题
使用时机：读完一篇教程 / 文档后立刻自测。比被动看书记得牢 3 倍。
我是 [背景：PLC 电工 / Qt 老手 / Python 入门 / ...]，
刚学完 [主题：OPC UA 信息模型 / Flux 查询 / pandas DataFrame / 3-sigma 异常检测]。

请出 5 道题测试我的理解：
- 题 1（最易）：[填空 / 选择]
- 题 2：概念对比 / 解释
- 题 3：内部机制 / 为什么
- 题 4：边界情况 / 实际应用
- 题 5（最难）：综合应用题 / 开放设计

要求：
1. 不要直接给答案，先给题目
2. 题目要结合我熟悉的工业场景（PLC / HMI / Modbus / 车间）
3. 每题标注考察的能力维度
💡 用法：AI 出题后自己先做，全部做完再问"现在给答案"。批改后标记错题 → 回去翻文档 → 找AI 出同类型题再做一遍。

1.2 代码实战题

适合练习特定 API / 库的使用
使用时机：看完文档想练手，但又想不出要做什么。
我刚学完 [主题：open62541 客户端 / Qt MQTT / InfluxDB Python 客户端]。

出 5 道代码题让我练手，由易到难：
- 题 1（5-10 行）：最基础 API 调用
- 题 2（20-30 行）：组合 2-3 个 API
- 题 3（30-50 行）：完整功能 + 错误处理
- 题 4（50+ 行）：含边界 + 性能考虑
- 题 5（开放）：自己设计场景实现

每题给出：题目描述 / 输入输出示例 / 评分标准（10 分制）。
不要给完整代码，只给题目和评分标准。
💡 用法：做完让 AI 帮你打分。如果某题得分低，回头看那一节 API 文档。

1.3 场景选择题（培养判断力）

适合学完多种技术后判断"用哪个"
使用时机：学完 Week 7 / Week 19 / Week 20 这类"选择"周。实战经验靠场景题练出来。
我刚学完 [A / B / C 三种技术 / 三种算法 / 三个协议]。

出 10 个真实工业场景题让我选：
- 5 题是 "该用 A 还是 B 还是 C"
- 3 题是 "如果只用 A，怎么实现 B 的功能"
- 2 题是 "这个场景下哪些绝对不能用"

每题场景尽量真实（如"老 PLC 改造""化工厂""水处理车间"）。
不要给答案，我选完后你评判 + 解释。
🚫 注意：如果你连选都不会，说明基础概念还没掌握，回去重读教程。

🧑‍🏫 2. 教练

2.1 苏格拉底式调试（不直接给答案）

适合编译错误 / 运行时错误 / 逻辑 bug 核心原则AI 只提问，不给答案
使用时机：卡住 15 分钟以上仍没解决。AI 直接给会害了你——下次还是不会。
我在 [场景：编译 / 运行 / 部署] 时遇到问题：

错误信息：
[粘贴完整错误]

我已经尝试：
1. [你的尝试]
2. [你的尝试]
3. [你的尝试]

环境：[Qt 6.8 / Windows 11 / MSVC 2022 / CMake ...]

请你扮演教练，用苏格拉底式提问引导我：
- 不要直接给答案或修复代码
- 先问 2-3 个澄清问题（如"CMake 怎么写的？"）
- 根据我的回答再深入
- 最后如果我真的想不出，再给提示
- 全程跟踪我的思考过程，记下"我假设错了的地方"
💡 为什么有用：调试能力 = 80% 排除法 + 20% 直觉。AI 帮你练习排除法，下次独立调试时能想到类似思路。

2.2 概念深化（追问"为什么"）

适合理解了"是什么"但不知道为什么
使用时机：读完文档后感觉自己"懂了"，但说不清原理。
我刚学完 [主题]，觉得自己懂了。但你能不能用 5 个"为什么"问题帮我验证：

例：
1. 为什么 OPC UA 用 Client/Server 而不是 Master/Slave？
2. 为什么订阅要分 PublishingInterval 和 SamplingInterval 两层？
3. 为什么 MQTT 用 QoS 而不是简单的 ACK？

要求：
- 5 个问题层层递进（从表层到原理）
- 每个问题前先告诉我"我假设的答案"，你来评判对不对
- 不要直接给我"正确答案"——让我自己想
- 如果我想错了，给我 1 个类比启发，而不是直接答案
💡 5 个"为什么"问完，你的理解深度能超过 90% 看过同一篇教程的人。

2.3 思路验证（我做了方案，让 AI 评估）

适合独立设计了架构 / 选型 / 流程后
使用时机：你做了一个设计决策（不是写代码，是"用什么 + 怎么组织"），想听听反馈。
我设计了 [某个方案 / 架构 / 流程]，请你扮演资深 [架构师 / DBA / 嵌入式工程师] 评审：

方案描述：
[粘贴你的设计文字 / 架构图描述 / 流程图]

重点请评估：
1. 可行性：技术上能不能跑通？
2. 可扩展性：加 10 倍数据量 / 加 10 个新变量时哪里崩？
3. 可维护性：3 个月后我自己（或同事）能看懂吗？
4. 性能：瓶颈在哪？
5. 成本：硬件 / 部署 / 学习成本
6. 跟我已有项目（Qt HMI）的集成点在哪？

先说 Top 3 问题，再给具体修改建议。不要客套话。

🔍 3. 审查员

3.1 4 维度代码审查（最常用）

适合每周交付物 建议所有写完的代码都过一遍这个审查
使用时机：写完一段代码后。**24 周计划里每周都建议做一次**。
扮演严格的资深 Qt / 工业自动化工程师，审查我的代码：

[粘贴完整代码]

请从这 4 个维度打分（1-10）：
- 正确性：逻辑对不对？边界情况处理了吗？
- 可读性：命名 / 结构清晰吗？3 个月后我自己能看懂吗？
- 性能：有没有明显浪费（轮询 / 字符串拼接 / 不必要的拷贝）？
- 健壮性：空指针 / 超时 / 异常输入 / 资源释放都处理了吗？

输出格式：
1. 总分：[X/40]
2. Top 3 问题（按严重程度）
3. 每条具体修改建议（可直接应用的代码片段）
4. 1 个"加分项"（已经做得好但可以更好的地方）
💡 关键：不要等"完美了"才让 AI 看。**写完就审**——及时反馈比延迟重要 10 倍。

3.2 集成代码审查（库与库之间的衔接）

适合集成第 3 方库 / 新协议 / 新模块
使用时机：Week 3 / Week 15 / Week 33 这种"集成新东西"的周。
扮演熟悉 [C 库集成 / Qt 跨平台 / 工业协议] 的架构师。

我刚集成 [库名 / 协议名] 到我的 Qt 项目，审查：

[粘贴：CMakeLists.txt + 集成代码 + 1-2 个使用示例]

重点看：
1. 依赖管理：库是源码 / 动态 / 包管理？版本如何锁定？
2. 接口封装：C 风格回调有没有包成 Qt 信号？线程安全吗？
3. 资源生命周期：库对象谁 new 谁 delete？Qt 父子对象机制用对了吗？
4. 错误传播：库的错误码 / 异常如何转成 Qt 的 emit errorOccurred？
5. 可移植性：Windows 写完了到 Linux 会有坑吗？

3.3 性能审查（针对性能瓶颈）

适合项目跑起来后怀疑有性能问题
使用时机：Week 22 / Week 23 这种性能 / 优化周。
扮演 Qt + 高性能 C++ 专家。

我的项目场景：[100 个传感器 × 1 秒 1 条 / 5000 个变量 / 24h 长跑]
代码：[粘贴热点路径，如 PollScheduler::onTick 或 InfluxDB 写入]

重点看：
1. 主线程阻塞：哪些调用是同步的？能不能异步？
2. 内存分配：有没有频繁 new/delete？reserve() 该用没用？
3. 字符串拼接：QString + 操作是否用 QStringBuilder / QStringLiteral？
4. 锁竞争：QMutex 该用没用？能不能改成 lock-free？
5. IO 模式：单条写入能不能批量？同步写能不能异步？

输出 Top 3 性能瓶颈 + 每条修复后预期提升的百分比。

🎭 4. 模拟器

4.1 扮 OPC UA / MQTT 服务器（生成测试数据）

适合需要模拟真实设备但环境没装好
使用时机：Week 1 / Week 9 测早期 demo，没有真实服务器时。
扮演 [OPC UA 服务器 / MQTT broker / Modbus 从站]。

场景：[工厂车间有 3 台泵，每台有温度/振动/电流 3 个传感器]。

请生成：
1. 3 个节点的描述（名称、数据类型、当前值、地址）
2. 模拟 24 小时的传感器数据（每 5 分钟一个点，正常波动 + 2 个异常点）
3. 输出 CSV 格式：timestamp,name,value
4. 异常点用注释说明（如 # 第 14:35 温度突变 → 模拟泵故障）

要求数据要"真"——不是完全随机，要有工业相关性。

4.2 扮客户 / 用户（需求反馈）

适合UI 设计 / 报表设计 / 功能取舍
使用时机：Week 12 / Week 21 这种设计周。无成本拿反馈。
扮演 [角色：不懂技术的工厂老板 / 车间操作员 / 自动化工程师 / IT 部门经理]。

我刚做完 [我的设计 / 报表 / dashboard]，给你看：
[粘贴截图描述 / 文字描述 / ASCII 图]

请用你的角色口吻反馈 5 条：
1. [角色] 第一眼看到了什么？
2. 哪些 [功能 / 数据 / 文字] 看不懂 / 不关心？
3. 哪些地方让你 [担心 / 困惑 / 不耐烦]？
4. 你希望 [多看到 / 少看到 / 改] 什么？
5. 如果给你 [3 分钟 / 30 秒] 看，你会看哪几个关键点？

不要客气，按 [角色] 的真实反应给。

4.3 扮测试工程师（边界条件 / 异常场景）

适合写完一段代码，准备进 24h 长跑前
使用时机：Week 22 长跑前 / 每次写完关键代码后。
扮演有 10 年经验的测试工程师。我刚写完 [你的系统/模块]。

请帮我列 10 个**最容易炸**的边界场景，让我提前补：
1. 网络相关的（断网 / 慢网 / 高延迟 / IP 冲突）
2. 数据相关的（空值 / 越界 / 0 值 / 负值 / NaN）
3. 并发相关的（同时多客户端 / 资源竞争 / 死锁）
4. 资源相关的（磁盘满 / 内存耗尽 / 文件锁）
5. 时间相关的（时间戳乱跳 / 时区切换 / 跨日 / 闰秒）

每条给出：
- 测试场景描述
- 预期系统的正确行为
- 我代码里最可能漏的位置（你猜）

4.4 扮面试官（终极验收）

适合Phase 收官 / 阶段性复盘
使用时机：Week 8 / Week 16 / Week 24 这种"复盘"周。
扮演 [角色：自动化公司技术总监 / Qt 架构师 / SCADA 厂商工程师]。

我刚学完 [主题：OPC UA / 时序数据库 / 异常检测]。

按你的角色风格问 10 个问题，由浅入深：
- 1-3 题：基本概念 / 你怎么用
- 4-6 题：内部机制 / 为什么这么设计
- 7-9 题：边界 / 异常 / 故障处理
- 10 题：开放设计题 / 你怎么看 X 趋势

要求：
- 一次只问 1 题，等我回答再继续
- 答错先指出哪里错，再问是否需要提示
- 最后给我评分 + Top 3 薄弱环节

🌉 5. 概念翻译器

5.1 用工业场景类比陌生概念

适合任何概念理解不了的时候
使用时机：看到新名词 / 新架构 / 新算法，立刻用这个 prompt。
我是 [PLC 电工 / Qt 老手 / Python 入门 / 后端工程师]，[行业] 出身。

要学的新概念是：[概念名]。
我对它完全陌生，看了文档还是觉得抽象。

请用 1 个我**真懂**的场景类比它，要求：
1. 类比必须来自我熟悉的世界（PLC / HMI / 车间 / 流水线 / 数据库表）
2. 不超过 200 字
3. 末尾给 1 个"反例"——说明类比的局限（避免我过度类比误解）
4. 如果实在不好类比，明确告诉我"这个概念需要先理解 X 才能懂"

例：
- 我熟悉的："OPC UA 节点"
- 我要学的："Kubernetes Pod"
- 类比："Pod 像一个车间班组……"

5.2 把"高级术语"翻译成"大白话"

适合读文档时被术语卡住 
我读 [OPC UA / InfluxDB / Kafka / ...] 文档，下面这段话看不懂：

[粘贴文档原文 1-2 段]

请：
1. 用"外行都能懂"的白话翻译
2. 标出这段里最关键的 3 个名词，单独解释
3. 给 1 个真实工业例子说明它在干嘛
4. 如果有图能说清楚，文字描述 1 张图

5.3 概念对照表（横向对比）

适合学完 2-3 个相似概念后整理 
我刚学完 [A / B / C 三种类似的技术]，给我做 1 张对照表。

要求维度：
1. 设计目标（各自解决什么问题）
2. 适用场景
3. 性能 / 资源消耗
4. 学习成本
5. 生态成熟度
6. 在我的 Qt 项目里用哪个？

每格不超过 50 字。最后给 1 个结论："如果你是 X 场景，选 Y"。

🔧 6. 调试助手

6.1 错误日志分析

适合有完整错误信息时 
我遇到错误，日志如下：
[粘贴完整错误日志 / 异常堆栈 / qDebug 输出]

环境信息：
- Qt 版本：
- 操作系统：
- 编译器：
- 相关库版本：

请你：
1. 按可能性排序 Top 3 原因
2. 对每个原因给"如何验证"的方法（让我能确认是不是它）
3. 给修复代码示例
4. 列出我应该查文档的关键词

6.2 偶发 bug（最难的那种）

适合运行 10 次挂 1 次 / 24h 跑挂 1 次 
我的程序有个**偶发 bug**：描述现象 + 触发频率。

描述：
[粘贴现象]

触发频率：[如 "24h 跑出现 1-2 次" / "重启后第一次出现" / "特定操作后"]

我已排查：
1. [做了什么]
2. [做了什么]

请你扮演调试高手：
1. 这是"什么类型"的 bug（资源竞争？时间相关？状态污染？）
2. 在我代码的哪些位置最可能？[粘贴代码关键片段]
3. 我该怎么写 1 个**能稳定复现**的测试？
4. 加什么日志能定位？
6. 临时 workaround 是什么？

6.3 性能分析（找瓶颈）

适合程序能跑但慢 / 资源占用高 
我的程序 [场景描述]。

性能数据：
- CPU 占用：[如 30%]
- 内存：[如 200MB 持续增长到 1.5GB → 怀疑泄漏]
- 接口耗时：[如 100ms]
- 数据库查询：[如 5s]

请你：
1. 指出 Top 3 怀疑对象（哪段代码 / 哪个环节）
2. 教我怎么用 [Qt Creator Profiler / Valgrind / Perf / Visual Studio Profiler] 验证
3. 给出至少 1 个**优化预期百分比**和修复方向
4. 警告我哪些"看似慢但其实没问题"的红鲱鱼（避免过早优化）

🎤 7. 面试官

7.1 模拟面试（找工作用）

适合真正找工作前的演练 
我要面试 [岗位：Qt 工程师 / 工业自动化开发 / 嵌入式开发]。
背景：PLC 电工 5 年 + 自学 Qt 1 年 + 自学智能工厂 6 个月。

请你扮演该公司资深面试官，按真实面试流程：
1. 自我介绍（2 分钟）—— 给我 1 个引导问题让我开始
2. 项目深挖（10 分钟）—— 我会讲我的 HMI 项目，你要问 3-5 个有深度的追问
3. 技术基础（10 分钟）—— 问 5 个 Qt / C++ / 多线程相关
4. 业务能力（5 分钟）—— 问 2 个工业场景题（如"客户投诉 PLC 通讯断了你怎么排查"）
5. 反问环节—— 给我 3 个反问问题模板（让我反问你）

规则：
- 一次只问 1 题，等我回答再继续
- 答错先指出哪里错，必要时给提示
- 全程打分，最后给我评分 + Top 3 准备方向

7.2 应聘简历润色

使用时机：写简历时。
我的简历草稿（项目经验部分）：
[粘贴 1-2 段]

请你扮演资深 HR + 技术面试官：

2. 改写示例（用 STAR 法：Situation / Task / Action / Result）
3. 给量化建议：哪些数字该补（用户量 / 性能提升 / 节省时间）
4. 关键词建议：[岗位 JD 关键词] 应该在简历里出现几次

7.3 自我介绍打磨

我要面试 [岗位]。
我的背景：[PLC 电工 5 年 + Qt 自学 X 月 + ...]。

帮我写 3 个版本的自我介绍（不同长度 / 不同侧重）：
1. 1 分钟版（电梯演讲）
2. 3 分钟版（详细版）
3. 突出 [某个能力] 的版本

要求：

📖 使用说明

💡 5 个让 AI 输出更好的小技巧

  1. 给 AI 角色背景（"我是 PLC 电工 + Qt 老手"），输出会量身定制
  2. 给 AI 角色定位（"扮演资深 DBA"），输出会从那个视角看
  3. 明确"不要给答案"（如果是练习题），避免 AI 把活全干了
  4. 贴完整上下文（代码 + 错误 + 环境 + 你已做的尝试），AI 一次答对率高
  5. 要格式（"先说问题，再说修复"），AI 输出更结构化

⚠️ 4 个绝对不该用 AI 的场景

  • 急停 / 安全联锁代码 —— 必须自己懂每一行，工业事故代价高
  • 不理解就直接抄 —— 你会 debug 一辈子，下次还是不会
  • 关键配置文件（证书 / 密钥 / 产线 IP） —— 不能给 AI
  • 你自己公司的专有逻辑 —— 上传给 AI 可能有泄密风险

📊 评估 AI 输出是否可信

每条 AI 输出前问自己 3 问：

  1. 这代码我能逐行解释吗？ 不能 → 不要用
  2. 跟官方文档对得上吗？ 不对 → 优先信文档
  3. 边界情况处理了吗？ 没处理 → 补上

如果 3 问都过，可以信。如果任何 1 问过不了，要么回头补基础，要么查文档。
