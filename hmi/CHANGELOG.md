### fix(tag): G-23 —— 派生变量:存不住、算不出、还冒充寄存器

> ★ 详见 `docs/现状.md` 第七节【G-23】。

体检给出的第三条是"派生变量"这一组,它最后拆成**三件独立的事**:

1. **存不住**:`expression` 字段**从来没进过 JSON**
   ⇒ 派生量存盘后变回**普通变量** ⇒ `PollScheduler` 去读 **plc1 的 0 号寄存器**,
   把现场数据顶掉计算结果(**不报错、不告警** —— 静默失败)。
2. **算不出**:`VariableManager` 的注释写着"依赖的 variable setValue 时自动触发重算",
   而**代码里一行 `connect` 都没有**
   ⇒ PLC 回包 / UI 改值 / 联动写源变量,派生量一律**纹丝不动**,画面显示的是上一次的旧值。
3. **冒充寄存器**:派生量 `address=0` 那是**真的 plc1 0 号寄存器**
   ⇒ 界面改一下就 `markDirty` → `WriteScheduler` 把它**发给现场**。

**修法**:`expression` 进 JSON(普通变量写空串)+ 读回时**先解析后建对象**并恢复派生标记
与依赖;表达式不合法 / 依赖不存在 ⇒ **整个加载失败**并点名是哪个派生量缺了哪个依赖
(检查放在**所有变量加载完之后** —— 派生量可以引用排在它后面的变量);
`VariableManager` 接上 `Variable::valueChanged` ⇒ 自动重算
(**队列 + processed 集合**:派生链会连锁、环最多转一圈、不爆栈;
依赖**存在但还没值** ⇒ 静默跳过,依赖**压根不存在** ⇒ 明确警告);
`Variable::setValue` **拒收**对派生量的写。

**测试**:新增 `tst_DerivedVariable`(13 条)+ `tst_PollSchedulerDerived` 加 1 条
("从工程文件读回来的派生量**永不被轮询**")。负向对照 **5 个变异全红**。

★ **顺带挖出一条【假绿】用例**:`tst_PollSchedulerDerived::derivedValue_isNotOverwrittenByRegisterZero`
原来写的是 `speed->setValue(3)` —— `int` 给 `Int16` 变量,而 `Variable::setValue`
做类型校验**拒收** ⇒ 两个源变量从头到尾**没有值** ⇒ 派生量算不出来
⇒ `QCOMPARE(after, before)` **恒真** ⇒ 那条"盯**值不被寄存器顶掉**"的用例
**从写下来那天起就是假绿** —— 它压根没测到"被顶掉"这件事。

★ 那条用例原来还钉了一句 `QCOMPARE(after, before)`(= "派生量的值不被任何人改"),
**这个钉法本身是错的**:源变量变了,派生量是它的函数,**就该**跟着变 ——
要求它不变等于要求派生量**撒谎**。⇒ 改成钉真正的不变式:
① 派生量**永远等于**源变量的表达式算出来的值;② 派生量**永远不是**某台 PLC 的 0 号寄存器内容。

### fix(plc): G-20 —— 调试面板的从站号被 `ok` 覆盖 ⇒ 写请求变成【广播写】

> ★ 详见 `docs/现状.md` 第七节【G-20】。

⇒ 而 `toInt` 失败时**返回 0** ⇒ `slaveId = 0` ⇒ **Modbus 广播地址**
(发给总线上**每一台**设备),界面上还显示"写成功"。

★ 更狠的是第二条路:**"连不上→排队→连上→发"**里 `executePendingModbus()`
**重新读了一遍 UI 上的文本** —— 那一读**绕过了全部校验**。

**修法**:整块搬进**公共层** `src/plc/ModbusRequestParser.{h,cpp}`
—— **先解析、后动作**,返回一份**已经校验过**的 `RequestSpec`;
`pendingModbus_` 的类型从 `PendingModbusRequest` 换成 `RequestSpec`
⇒ **排队的就是刚校验过的那一份**(含从站号);`executeModbus()` 不再碰 UI。

★ 这条以前【测不到】:解析逻辑**全写在 `hmi.cpp` 里**,而 `hmi.cpp` **不在 `hmi_core` 里**
⇒ 单测**编不到**它 ⇒ 以前的测试只能"抄一份跑"(测的是副本,不是生产代码)。
搬到 `src/plc/` 之后,测试调的是**生产用的同一个函数**。

**测试**:新增 `tst_ModbusRequestParser`(纯逻辑、只依赖 QtCore):
从站号非数字 ⇒ 失败、**绝不返回 0**;从站号 **1-247**(0=广播、248-255=保留,都拒);
地址 0-65535;寄存器 读 1-125 / 写 1-123,位 读 1-2000 / 写 1-1968;
写值列表**保留 `0x` 前缀**,而从站号/地址**只认十进制整数**。

### fix(logging): G-19 —— 日志目录打不开时,每条日志都重试一次(P0 → P2)

> ★ 详见 `docs/现状.md` 第七节【G-19】。

**★ 本条首先是【推翻我自己的一个 P0 结论】★**
体检时我给的 P0-1 是"日志文件打不开 → `messageHandler` 里 `qWarning` → **重入**
`messageHandler` → 二次 `lock` 同一把非递归 `QMutex` → **同线程死锁**"。
探针 `tst_QtReentryProbe.cpp` 实测:**Qt 6.8.3 不会重入自定义消息处理器**
(handler 内部再打一条日志,Qt 交给**默认 handler**,自定义 handler 一次都没被重入,
实测 `entered=1 / reentered=0`)⇒ **那条死锁链不成立**,本条 **P0 → P2**。

**真正的缺陷(P2)**:日志目录打不开时(磁盘满 / 无写权限 / 配置路径写错),
每**一条**消息都走一遍 `QDir().mkpath()` → `QFile::open()` → 报错
⇒ **stderr 被刷爆、CPU 白烧,而日志文件一个字也没写进去**
—— 典型的"**失败路径比成功路径还吵**"。

**修法**:`State` 加 `fileBroken`(打不开一次就记下来,**不再每条重试**;
等【换日】或【换配置】才再给一次机会);
handler 内部改用 `fprintf(stderr, ...)` 不走 `qWarning`
(出来是**裸文本**,而且**不受本模块的级别过滤控制**);
抽出 `closeCurrentFile()`,`delete` 后**立刻把指针置 `nullptr`**
(原来那一瞬间是**悬垂指针**);`applyConfig()` 复位 `fileBroken`;
暴露 `Diagnostics{reentryCount, openAttempts}` 让测试能**精确**断言"没有反复重试"。

★ 留下的 `reentryCount` 在今天的 Qt 上**恒为 0** —— 它不是"修好了"的证明,是**哨兵**:
哪天 Qt 改了这条语义,它会**先红**,而不是等到现场发现程序不动了。

★ 教训:**"我以为会死锁"和"实测会死锁"是两件事** ——
凡是说"这会死锁/这会崩"的结论,**先写个探针把它跑一遍**。

### fix(trend): G-18 —— 趋势曲线会【少一个点】,根因是一个 1 毫秒的时钟竞态

> ★ 详见 `docs/现状.md` 第七节【G-18】。

**现象**:变量变了,曲线却没多一个点。
GitHub Actions 上 `tst_Trend` 红过(2026-10-22,run #18),但**日志里一行断言原文都没有**
⇒ 它以"偶发、未复现、没取到断言原文"的形式**在本仓库悬了两个月**(10-25 / 10-26 各记一次)。

**根因**:`TrendWidget::onVariableChanged` 取了**两次**时钟 ——
窗口上界 `currentDateTime()` **先**取、数据点时间戳 `currentMSecsSinceEpoch()` **后**取。
两次读之间只要跨过 1 毫秒边界,`nowMs` 就比窗口上界大 1ms
⇒ 而判的是 `nowMs > to ⇒ 不在窗内 ⇒ 丢` ⇒ **这个实时点被当成"窗外"扔了**。
实测**单点丢点率约 2%**,而且**一条日志都没有** ——
曲线上持续有缺口,用户看到"曲线偶尔少一个点",查不出原因。

**修法**:**只取一次时钟**,窗口和数据点共用同一个"现在"
(`rangeWindow()` 改成收 `now` 参数、内部不许再取时钟;`reloadFromHistory()` 同样)。

**回归钉子**:`tst_Trend` 新增 `realtimePoint_isNeverDroppedAtWindowEdge`
—— 一个用例函数里连做 200 次(单次撞上只有 2%,一次断言等于没钉)。
负向对照:带 bug 的代码 **20/20 红**(第 1…189 次随机丢点);修复版 **100/100 绿**。

**附带记一笔(比修复本身更值钱)**:
"修完还是红"查下来是**编译产物里留着旧代码** ——
用 `Copy-Item` 恢复源码会**保留旧 mtime**,若比已编译的 `.obj` 还旧,
ninja 判定"已是最新" ⇒ **不重编** ⇒ 跑的还是带 bug 的旧实现。
⇒ 规矩:恢复源码用 `git apply` / `git checkout --`;
**恢复后核对构建日志里有没有 `Building CXX object ...TrendWidget.cpp.obj` 这一行**
(只有 `Linking` 没有 `Building` ⇒ 源码根本没进编译)。

### feat(soak): SOAK-W —— 24h 长跑的写侧闸(整体重做)+ BUGFIX-E3 修完

> ★ 详见 `docs/现状.md` 第七节【G-17 §六之六】。

**背景**:BUGFIX-E1 修之前是"读 547 次全成功、写 604 次全被拒、0 帧落地",
而长跑的活体判据(SOAK-6)**只看读** ⇒ 那种情况下**照样绿**。
⇒ 长跑里必须有一道**独立的写侧闸**。

**★ 原设计被三条实测推翻,整个换掉 ★**

| # | 实测 | 推翻了什么 |
|---|---|---|
| 1 | 拒收行是 `qCWarning` ⇒ **默认级别就看得见** | "必须开 debug 才看得见"(错) |
| 2 | 开 `hmi.comm=debug` ⇒ 893 行/分 ⇒ 24h ≈ 129 万行,而 `Get-LogSince` `limit=50000` **到顶就停止读** ⇒ 只看得到前 0.9 小时 ⇒ **所有判据被截断** | "长跑要写 `hmi.json`"(它会毁掉整轮) |
| 3 | 真断线**不产生**"Modbus 错误"(那在 UI 层,`onSocketError` 故意不发 `errorOccurred`),且断线会作废排队写 | 整套"时间窗口猜环境 vs 缺陷"的判法 ⇒ **必然误报** |

**改成:让程序自己说。** `ModbusMaster` 加一条 **INFO 级 / 60 秒一条**的写侧统计行
(累计计数 + 拒收原因分类)。"环境问题还是缺陷"由**程序在它知道原因的地方**判定
(`None`/`NotConnected`/`Invalid`/`QueueFull`/`SendFailed`),
harness 只负责取数 + 判恒等式 + 跟从站日志交叉核对。

**三条会计恒等式**:①`已发出 == 成功 + 失败 + 在途写` ②`排队 == 排队发出 + 排队作废 + 在队`
③`拒收 == 未连+非法+队列满+发送+缺陷`。任何一条残差 ≠ 0 ⇒ FAIL。

**fix(BUGFIX-E3)**:写请求收到 **Modbus 异常响应(FC|0x80)** 时,
`finalizeErrorReply` **只给读发 `readFinished`** ⇒ 写永远收不到 `writeFinished`
⇒ `WriteScheduler::pending_` 永久泄漏 ⇒ `inflightPerPlc_` 降不下来
⇒ **那台 PLC 从此再也不写任何东西,而且零日志**。

**★ 判据自己也有一个假绿(现场挖出来的)★**
`Get-WriteSideStats` 只报窗口增量 ⇒ 窗口里**只有一条**统计行时增量恒为 0,
判据报"写尝试 0 次(没写过)"—— ★ **事实相反的话** ★
(那一行明明写着 `尝试=541 拒收缺陷=541`)。
**修法**:坏路径(拒收缺陷/队列满)按**绝对值**判(坏路径是二进制的属性,不是窗口的属性),
流量按**增量**判;算不出差时明说"**验不全**",**不再说"没写过"**。
⇒ 同一行日志:修前 `UNKNOWN`(exit 4)→ 修后 **`FAIL`(exit 1)**。

**实测(2026-10-28)**:

>
> | JSON | typeId | typeName |
> |---|---|---|
> | `0` / `-1` / `70000` | 4 | `qlonglong` |
> | `0.5` | 6 | `double` |
> | `"0"` | 10 | `QString` |
>

### fix(poll): 轮询回包会把联动刚写的值【冲掉】—— 发出去的是另一个数

> ★ 详见 `docs/现状.md` 第七节【G-16】。
> ★★ 这是上一条(G-15)【第八节】自己列出来的"已知,本次没修",这次修掉了。

**现象**:联动(`"温度高" → Speed 写 0`)执行后,在动作写完到
`WriteScheduler` 下一拍(100ms)之间,轮询回包到了:

```
t=0        动作把 Speed 设成 0 并 markDirty      -> 本地值 = 0
t=0~100ms  轮询回包带着【PLC 里的旧值 100】
           -> 原来这里无条件 v->setValue(100)     -> 本地值被冲回 100
t=100ms    WriteScheduler 下一拍【现取 v->value()】-> 发出去的是 100,不是 0
```

**现场表现**:界面显示停机成功、审计记着"写了 0"、**PLC 上跑的还是老转速**。
(`buildWritePayload` 是在 `onTick` 里**现取** `v->value()` 的,不是动作那一刻拍下来的。)

**★ 为什么这个洞能活这么久 —— 仓库里早就有人写下它,然后绕开了它:**

- `tst_PlcMultiServerE2E.cpp:567-596` 的注释逐字写着
  "读会 setValue 覆盖本地值,而 WriteScheduler 在 onTick 里现取 v->value(),
  两者一起跑就有真实竞态" —— **判断是对的**,但它把这事当成了**测试的障碍**,
  不是**一个 bug**。于是被"测试绕开"而不是"代码修掉"。
- 本该抓住它的 `tst_ActionWrite.cpp`,mock 的 `sendReadRequest`
  是 `return true;` —— **什么都不做** ⇒ 那个文件里没有任何一条用例碰得到读通路,
  而这个 bug **整个住在读通路上**。

**修法**:

- `hmi/PollScheduler.cpp`(`onDriverReadFinished`)加守卫:
  `const bool writePending = v->isDirty() && v->access() == Variable::Access::ReadWrite;`
  —— **只跳过 `setValue` 一行**,`setQuality(Good)` / `emit rawRead(v, raw)` /
  `nextPollAtMs_` **三样照做**。理由(每一条都有代价):
  跳过 `setQuality` ⇒ `ThresholdAlarmChecker::onRawRead` 头一行
  `quality == Good` 不成立 ⇒ **整个报警系统对这个变量哑掉**;
  跳过 `rawRead` ⇒ **报警不再触发**,而**报警正是联动的触发源**;
  跳过 `nextPollAtMs_` ⇒ 每帧都重发读请求 ⇒ **把总线打满**。
- ★ 条件里带 `access() == ReadWrite` 是必须的:`WriteScheduler::onTick` **只发**
  `ReadWrite` 的变量,而 `ActionManager` **不检查 access** ——
  联动配了只读变量的话,它会被标脏却**永远写不出去**,
  这时候保护它的读回 = 那个值**永久停在联动写的值上**(引入一个新的"值不刷新"故障)。
- `hmi/WriteScheduler.{h,cpp}`:新增 `pendingSentValue_`,
  在 `buildWritePayload` **之后**取 `sentValue` 登记,`onWriteReply` 里

### fix(comm): 写被读饿死 —— 整个 24 小时可能【一个字节都写不出去】,而活体判据照常绿

> ★ 详见 `docs/现状.md` 第七节【G-17】。
> ★★ 这是 G-15 / G-16 之后的**第三个实例**,同一个形状:
>   **判据全绿,而被验的那件事压根没发生。**

**现象**(2026-10-26,`soaks/sweep_m85`,`min_duration=85`):

| 观察点 | 实测 |
|---|---|
| 从站 `FC6 写` | **0 条** |
| 应用 `[Write] 发写` 行 | **604** |
| 应用 `[Write] OK` 行 | **0** |
| 应用 `driver 拒收了…的写请求` | **604** |
| `[Action]` 联动行 | 21 |
| 轮询统计 | `发出=547 成功=547 失败=0` ← **读全都正常** |

★ **写一次都没出去,而读照常成功** —— 现场表现跟"联动没生效"一模一样。

**根因**(BUGFIX-E1):读和写**共用同一个在途槽**,
`if (!pending_.isEmpty()) 就拒收`。写节拍每拍都撞上一个在途的读
⇒ 写被读饿死 ⇒ `dirty` 一直留着、下一帧重试、下一帧又撞上。

★★ **这个洞的关键性质:它是【启动相位的一次抛硬币】,不是概率 ★★

写节拍和轮询节拍都是 **100ms 定时器** ⇒ **相位锁死**,
**相对偏移在进程启动那一刻定死了,之后一辈子不变**。

实测(同一套参数、只改 `min_duration`):

| `min_duration` | 写尝试 | 被拒 | 落地 |
|---|---|---|---|
| **85** | **604** | **604** | **0** |
| 70 / 88 / 92 / 95 / 97 / 99 | 几十 | **0** | **全部落地** |

⇒ **"哪个 m 会暴雷"不是 m 的性质,是那一次启动相位的性质。**
⇒ 推论一:**"我这个配置跑绿了"证明不了修好了。**
⇒ 推论二:**24h 长跑掷到坏的那一面,整场都在"写不出去"**,
  而读照常成功 ⇒ **长跑的活体判据(它数的是【读】)24 小时全绿。**

**修法**(BUGFIX-E1):写**排队**,不再被拒收。

| | 改之前 | 改之后 |
|---|---|---|
| 槽被占时的写 | **拒收**(nullptr) | **排队** |
| 调用方看到 | "被拒,下一帧重试" | "已受理,必定会有一个 `writeFinished`" |
| 值什么时候定 | —— | **入队那一刻**定死 |
| 队列满 | —— | 才拒收(上限 8) |

★ Modbus TCP 是**串行**协议,一条连接同时只能有一个未完成请求
⇒ 给读写各开一个槽会导致**帧交错** ⇒ **排队**才是对的修法。
★ 槽只有一个出口(`notifyIdleIfEmpty()`)⇒ flush 挂在那儿,
  读回包 / 超时清理 / 连接变化**三条路径一次全盖住**。
★ **值必须在入队时定死** —— 跟 BUGFIX-D1 同类(在"reply 时刻"取错值),这次是"发送时刻"。
★ **自己写错的第一版**:把"槽被占就排队"放在参数校验**前面**
⇒ 不合法的写也会被排队 ⇒ `values` 为空时 flush 出一个 `byteCount=0` 的**畸形帧**。
⇒ 校验在前、排队在后。

**★ 修的过程中挖出第二个洞(BUGFIX-E2)★**

断线 handler 和 `connectTo()` 原来都只是 `pending_.clear()` —— **不发任何失败通知**。
那些请求的 reply 上确实 `setError()` 了,
**但那只是给调用方的 `QModbusReply` 句柄**;
而 `PollScheduler` / `WriteScheduler` 等的是**信号**,不是那个句柄。

⇒ `PollScheduler::inFlight_` 和 `WriteScheduler::pending_`/`inflightPerPlc_` **永久泄漏**
⇒ 那台 PLC **从此不再读也不再写**,而且**零日志**。
★ 跟 2026-10-21 的"16.5 小时零轮询流量"(BUGFIX-C1)同一个形状,
  只是那次走协议级失败,这次走**连接断开/重连**。

**修法**:加 `ModbusMaster::failPendingRequests(reason)`,
断线和重连各调一次,**每个在途请求发一个失败通知**,
且**按读/写分流**(写发 `writeFinished`,读发 `readFinished`)。

**测试**:`hmi/tests/tst_ModbusWriteQueue.cpp` **11 条用例**(新增)。

**负向对照**:`scripts/negctl_write_queue.py` —— **7 个变异**
(W1 拆排队分支 / W2 排队时不存值 / W3 重连不作废 / W4 不发 `writeFinished` /
W5 校验挪到排队后 / W6 断线不通知 / W7 重连不通知)。

### fix(logging): 日志级别过滤把告警【全吞了】—— 整个应用一条告警都写不进日志

> ★ 这是做上面那个联动负向对照时**顺带挖出来的**,
> 但严重程度**比它还大**:① 是**一条**联动没生效;②是**整个应用的告警能力**从第一天起就是瞎的。

**根因**:`QtMsgType` 的枚举值【**不是按严重程度排的**】(实测 Qt 6.8.3):

```
QtDebugMsg    = 0
QtWarningMsg  = 1
QtCriticalMsg = 2   ← QtSystemMsg 也是 2
QtFatalMsg    = 3
QtInfoMsg     = 4   ← ★ Info 是【后加上去的】,数值比 Fatal 还大
```

`Logging.cpp` 原来是 `if (type < effLevel) return;`,
而**默认级别就是 `QtInfoMsg`(= 4)** ⇒ `Warning(1) < 4` ⇒ **全部丢弃**。
`Critical(2)`、`Fatal(3)` 同样被丢。

**实测证据**:

- 24 小时长跑的两份应用日志(891 + 2026 = **2918 行**),
  **级别分布 = `INFO` 2918、`WARN` 0、`CRIT` 0、`FATAL` 0**。
  (唯一的 1 条 WARN 在 `runner.log` 里,是长跑脚手架自己打的,不是应用打的。)
- 启动期那条**固定会出现**的告警 —— `hmi.cpp:311` 的
  `qWarning() << "[协议可用性] S7 尚未实现..."` —— 在 24 小时日志里**一次都没出现过**。
- 修完之后同一条日志里就有了(修后短跑实测):
  `[WARN ] default - [协议可用性] "S7(未实现)" 已在下拉框置灰: ...`

> ★★ 这个洞**伪装得很好**:日志文件在长大、轮询统计在打、界面一切正常 ——
> 只有"出事的时候日志里什么都没有"这一个症状。
> BUGFIX-C1(2026-10-21)查"16.5 小时零轮询流量"时,根因就是一条同类的静默路径,

比【严重程度排名】,不比 `QtMsgType` 数值:

### fix(alarm): Below 方向的报警判据重叠 —— 24 小时里同一条报警重复报了 11568 次

★ **SOAK-2 内存线性增长的机制之一,已定因并修掉。** 详见 `docs/现状.md`
第七节【SOAK-2 到底是个什么东西】。

#### 现场(长跑实测,不是推算)

`soaks/20261021_164804/appdata/QianWei/HMI/history.db` 的 `alarm_history` 表:

| 报警 | 方向 | 触发次数 | 触发间隔 | 触发值实测 |
|---|---|---|---|---|
| 温度高 | Above 50 | **460** | 188 秒(三角波半周期) | 51 / 52 |
| 温度低 | Below 10 | **11568** | **0.44 秒** ★ | **0~9,从未回到 10 以上** |

「温度低」的触发序列:时刻 0.000s 值 8 → 0.464s 值 8 → 0.884s 值 6 → ……
**值一直在 0~9,从来没真的恢复过**,却每 0.44 秒报一次。
这是**重复触发**,不是"高→正常→再高"那种两次独立工况(后者是正确的工业语义)。

#### 根因:`ThresholdAlarmChecker.cpp` 的两个沿在 Below 方向重叠

```
Above:  触发沿 val >  T  → (T, +∞)   恢复沿 val <= T  → (-∞, T]   ★ 互斥 ★
Below:  触发沿 val <  T  → (-∞, T)   恢复沿 val <= T  → (-∞, T]   ★ 重叠 ★
```

Below 的恢复沿写成了 `!(val > recoveryLimit)`,`hysteresis=0` 时就是 `val <= T`,
**而触发沿是 `val < T`**。值 = 9 时两条**同时成立**("还超限" 和 "已经恢复"),
于是:报一次 → 立刻判恢复 → 下一个轮询周期再报。

**为什么 hysteresis 治不了它**:Below 的 `recoveryLimit = threshold + hysteresis`
在**上**,触发线在**下** —— 恢复区间必然**包含**触发区间,
所以 `hysteresis > 0` 只会让重叠区**变大**。这是滞回从落地起就有的方向性错误。

#### 改法

Below 的恢复沿要问"值是否已经**不**低于阈值",即
`!(val < recoveryLimit)`(= `val >= T + hysteresis`),不是 `val <= recoveryLimit`。

```
hysteresis=0 → 触发 (-∞,T) / 恢复 [T,+∞)     ★ 互斥 ★
hysteresis>0 → 触发 (-∞,T) / 恢复 [T+h,+∞)  ★ 互斥 ★
                且 [T, T+h) 是死区:不超限、也不算恢复 ★
```

—— 滞回终于在 Below 方向真正有用了(以前是反的)。
Above 那边的写法本来就是对的,**一个字没动**。

#### 测试(有牙齿的)

`hmi/tests/tst_ThresholdAlarmChecker.cpp` 新增两条:

| 用例 | 钉住什么 |
|---|---|
| `belowSustainedUnderThreshold_doesNotRetrigger` | Below 持续超限 → 报**恰好一次** |
| `belowWithHysteresis_sameShapeAsAbove` | Below 加滞回 → 死区 [T, T+h) 不算恢复,升到 T+h 以上才恢复 |

★ **为什么这两条以前不存在 ★**
**全套 F2 滞回用例清一色 `Direction::Above`,Below 方向一条都没有** ——
所以 Below 的判据重叠**从来没被任何测试执行过**,它在长跑里活了 24 小时。
(这跟 G-11 那个"三个星期没人发现"是同一类:测了上面,没测下面。)

脚本只结束自己启动时记下的那些 PID。

**★ 放大器从"多变量"改成"多 PLC"(2026-10-23 改写)★**

原设计是"对照组 3 个连续地址变量 vs 实验组 16 个非连续地址变量",
指望后者因为合并不了而多发 15 倍请求。**这个放大器是坏的,设计作废**:

- 非连续地址的工程,请求率上限被 `PollScheduler::onTick` 的单 in-flight
  防御钉在 **10 次/秒**(1 帧 / 100 ms)——
  第 2 批起撞上限流被拒收,BUGFIX-B1 回滚 `inFlight_` + `nextPollAtMs = now+100`。
  所以【一台 PLC 上的变量个数,基本不影响请求率】。
- 16 个变量实测只有约 2 倍(不是设计的 16 倍),**斜率不可换算**。
  (那个"约 2 倍"是推算:修复后只跑过 2 变量那组,实测 544 次 / 70 秒 = 7.8 请求/秒;
  16 变量那组还没跑。别把它当已验证的数字用。)
- 更糟的是:修复**之前**,这种工程第一个 tick 之后就不动了 ——
  实验组从站一个请求都收不到,而**闸门抓不到**:统计行照常每 60 秒出现,
  只是计数永远停在 1。差点拿废数据下结论。

**正确的放大器是【多 PLC】。** `dueByPlc` 按 `plcId` 分组,
**每台 PLC 有自己的 driver、自己的 `pending_`** —— 跨 PLC 不撞限流,
每台都能跑满自己的帧率,而每台内部仍然合批(连续地址还是 1 帧)。
N 台 PLC = N 倍请求率,倍数**可精确预期、可核对**。

改写后的 `scripts/mem_probe.ps1`:

| 组 | PLC 台数 | 每台变量 | 端口段 | 预期请求率(推算) |
|---|---|---|---|---|
| control | 1 | 3 个连续地址(0,1,2)→ 合批 1 帧 | 1510+ | ≈ 5 请求/秒 |
| treatment | **8**(`-PlcCount`) | 同上 | 1530+ | ≈ 40 请求/秒 |

> 这张表里的"预期"是**推算**(5.00 = 200 ms 一轮)。实测值见下一段:
> 单台 **4.55 /秒** —— 比推算低的那 10% 就是下面那条"90 折",不是放大器的问题。

变量两边**完全一样**,唯一差别是 PLC 台数 —— 斜率差只可能来自"请求数"。
每台 PLC 一个自己的从站进程,端口一一对应,两组端口段不重叠。
三道闸保留(卡模态框 / 等不够久 / 连错从站),其中闸三改成
**每组的每一台都要查**,不能只查第一台。

> ★ 闸三自己也有个 bug,顺手修了 ★
> 原写法 `-Pattern ([regex]::Escape($want)) -SimpleMatch` —— 两个开关互相抵消:
> `Escape` 把 `127.0.0.1:1510` 变成 `127\.0\.0\.1:1510`,而 `-SimpleMatch` 找的是
> **字面串**,于是它去找带反斜杠的那串,日志里当然没有 → **闸三永远挂**。
> (第一版只有 1 个端口时也是这么写的,只是从来没人跑过这个脚本。)
> 改成只用 `-Pattern` 靠 `Escape` 走正则,闸三才第一次真的会放行。

### fix(comm): 写响应的 echo 地址比对,是个【从没填上的占位】

`ModbusMaster::handleWriteResponse` 里这一行,从 2026-07-07 写下来到今天:

```cpp
if (echoAddr != quint16(req->reply ? /*addr 通过 reply 拿*/0 : 0)) {
    qCDebug(hmiComm) << "[ModbusMaster] 写响应 echo addr 与请求不一致";
}
```

三元的**两个分支都是 0**。所以它实际判的是 `echoAddr != 0`,
**不是**注释说的"与请求地址比对"。两个方向都错:

| | 现场 | 老代码的反应 |
|---|---|---|
| 正常写(地址非 0) | 回包 echo 也是那个非 0 地址 | 判成"**不一致**" —— 每一次正常的写都报一次假警报 |
| 真不一致,但回包地址恰是 0 | 请求 0x0100,回包 echo 0x0000 | 判成"**一致**" —— 真的不一致**一声不吭** |

换句话说:它抓的全是不该抓的,漏的全是该抓的。
而这行是 `qCDebug` —— 默认 INFO 级别下一行都不落,现场看不见。

**修法**:请求地址在**发出去的时候**存进 `Pending::startAddress`,回包时拿它比。

> 为什么不"回包时去拿"?`QModbusReply` 上**根本没有**请求地址这个信息
> (它只有结果数据)。原来那句 `/*addr 通过 reply 拿*/` 是个**空想** ——
> 改成 `req->reply ? addr : 0` 一样编不过、一样错。唯一正确的做法是发的时候存。

**只报警,不判失败**:沿用原来的取舍(有些从站实现宽松),
把写判成失败会让本来能用的现场直接瘫掉。但必须**看得见** ——
所以改走 `logCommError`(本文件既有的限速告警出口:第 1 次 WARNING,
之后 10 秒内降级到 Debug,每 10 秒补一条汇总),顺带解决了
"从站一直回错地址 → 日志被刷爆"。

★ 消息里**带出两个地址**(回包是哪个、请求是哪个)——
只说"不一致"的话,看日志的人还得自己翻请求那一行才知道差在哪。

**协议事实**(别搞错):写响应(0x05/0x06/0x0F/0x10)回显起始地址;
**读响应(0x01~0x04)只有 byteCount + 数据,没有地址字段** ——
所以只有写能比,给读加一个"地址比对"是把协议读错了。

**回显地址恰是 0 也必须报**(老代码唯一完全看不见的那一种)。

### fix(project): 删掉一个变量,这个工程就再也打不开了

**病**:变量被删掉之后,还有报警/联动引用着它。这时候再点保存,
存出来的工程**整个打不开**。

```
用户删掉变量 Temp
   ↓
报警 "炉温高" 还在引用它
   ↓
点保存
   ↓
存出来的 JSON 里,那条报警的 variable 是 ""
   ↓
下次打开 → findVariable("") 拿不到 → failWith → 【整个工程打不开】
```

现场表现是"我明明存成功了,怎么打不开了",而且**无从推断**:
界面那边删变量时根本没提示过(界面那侧是拒删的,这条路只有数据层能走),
日志里也没有一句"这条引用是悬空的"。

**两个坏法不一样,所以只修一个不够**:
- 报警侧:`ThresholdAlarmChecker` 存的是 `QPointer<Variable>`,变量没了它就变空
  (`ThresholdAlarmChecker.h:121-125` 那段注释明说:"QPointer 解决的是
  【不该崩的地方不崩】,不是【不该写坏的文件不写坏】")→ 存盘时写出空串。
- 联动侧:`ActionManager::Mapping` 存的是**变量名字符串**
  (`ActionManager.h:66`,故意不存裸指针)→ 变量没了那个名字**原样留着**,
  文件里 `"Temp"` 看着挺正常,**肉眼看 JSON 根本找不出哪里坏了**。

**修法**:存盘时跳过悬空的那条,并在日志里点名。
为什么是"跳过"而不是"报错不让存":报错不让存 = 用户被卡死在
"我删了一个变量,现在存不了了",而他删那个变量时界面根本没提示过;
写出去 = 整个工程(不只是那一条报警)全丢。两条路里,丢一条已经没用的报警
比丢整个工程轻得多。而且报警引用的变量已经没了,它本来就不可能再触发。

★ 变量名在变量被删的那一刻就没了(QPointer 变空,没人记得它叫什么),
所以没法"保留报警配置只清掉引用" —— 只能整条跳过。

**测试**:`tst_ProjectMultiPlc` 新增
`danglingReference_isSkipped_butValidOnesSurvive`。
为什么必须新增而不是只把老的两条修绿:那两条只断言"存出来的工程能打开",
而"**什么都不写**"也满足这个断言 —— 空的 alarms 数组在加载时循环体一次都不进,
工程照样打得开。老的两条【结构上就抓不住】"好的被一起砍掉"这种实现。

**负向对照 —— 实测两轮**:
- 轮次一:修法换成最粗暴的版本("所有报警和联动统统跳过")
  → **红 1**(只有新用例),绿 23。老的三条**照样绿** —— 正是上面说的那个洞。
- 轮次二:bug 原样装回去
  → **红 3**(老的两条 + 新用例),绿 21。

两轮合起来才说明修法是对的:一轮证明"新用例补的是老用例够不到的洞",
一轮证明"红是真的因为 bug 在"。

`Copy-Item` 会把源文件的旧 mtime 一起带过去,而 ninja 只看 mtime。
现象是"源码明明修好了,测试还是红的"—— 假红会让人去改本来正确的代码。

|---|---|---|

| D | 从站 `slave.log` 还在不在长 | 从站死了 |
| E | ★ **成功读次数还在不在涨** | ★ **程序活着但业务停了** |

**「进程还在」不是活着的证据,「成功读次数还在涨」才是。**
应用日志每 60 秒打一行 `轮询统计:发出=… 成功=…`,看门狗就盯这个字段。

健康 / harness 死 / verdict 停更 / 被测退 / 从站死 / 成功不涨 / 没有统计行 /

### fix(poll): 轮询统计行的格式对不上 —— 判据一次都没匹配上

长跑的启动自检等满 **120 秒**,一条轮询统计行都没匹配上,判成
「这一轮没资格跑」—— 而那 120 秒里程序**一直在正常轮询**
（成功 271 次、失败 0 次）。**判据坏掉的样子,和程序坏掉的样子,一模一样。**

根因是两边对不上:

| | 格式 |
|---|---|
| 程序**真打出来**的 | `轮询统计:发出= 271  成功= 271  失败= 0`（等号后有空格） |
| 判据要的 | `轮询统计:发出=271 成功=271 失败=0` |

那个空格哪来的:**QDebug 在相邻两项之间插一个空格**。于是
`qCInfo(cat) << "发出=" << count` 出来的是 `发出= 271` —— 而不是
`PollScheduler.cpp` 里那段注释写的、也是 harness 正则认的 `发出=271`。
**程序一直在违反自己的文档**,而没有任何测试发现它。

**为什么能潜伏这么久**:判据自带的验证脚本 `verify_soak6_liveness.ps1`
**一直绿** —— 因为它喂给判据的是 `发出=123`（没空格）,
那是**它自己想象的格式**。一个拿自己当参照的测试,证明不了它和现实对得上。
2026-10-21 那次 950.9 分钟的长跑,`SOAK-6` 这条判据**一次都没真正判过**。

四处同时改:

- `PollScheduler::formatStatsLine()`:整行拼成**一个**字符串再输出,
  QDebug 就没有可插空隙的地方了 → 输出与它自己注释里的格式一字不差
- `long_run.ps1` 的 `$rePollStats`:等号后**允许空白**(`\s*`)
  ⇒ 判据对**新旧两个二进制都有效**（那台机器上还挂着一个旧二进制在跑）,
  而字段名/顺序改了照样会失配（那才是要命的）
- `verify_soak6_liveness.ps1`:改用**从真日志里原样抄下来的黄金样本**,
  并加了两条:新旧两种格式都判 PASS、格式漂移必须判 UNKNOWN（**要响**）
- 新增 `tst_PollStatsFormat`:把 `long_run.ps1` 里的 `$rePollStats`
  **原样读出来**,去匹配程序**真的打出来的那一行**
  （真调度器 → 真轮询 → 真计数器 → 真日志行 → 判据的正则）。
  单独钉程序那一侧没用 —— 两边照样能各改各的、一起漂走。

**负向对照**（改前绿、改后精确红）:判据正则退回旧式 → 红 2;
程序格式退回带空格 → 红 2。

### feat(scripts): 长跑实例与已经在跑的实例共存（不动它一个字节）

### fix(crash): 崩溃 dump 的消费端断了 28 天 —— 写和读的不是同一个目录

`crash/pending.txt` 停在 `2026-09-16T09:34:10` / `exception_code=0xC0000005`,
**92 次启动从它身边走过,全程零报错**。

根因不是逻辑 bug,是**路径算错了地方**。`dumpDirectory()` 用
`QStandardPaths::AppLocalDataLocation`,它含 `<org>/<app>`,而 `main.cpp`
把 `setOrganizationName/setApplicationName` 排在 `crash::install()` /
`hasPendingDump()` **后面**:

| 时机 | org/app | 落点 |
|---|---|---|
| **崩溃发生的那一瞬间** | ✅ 早已设好 | `AppData/Local/QianWei/HMI/crash/` ← dump 真在这 |
| 启动时 `hasPendingDump()` | ❌ 未设 | `AppData/Local/crash/` ← 从没写进去过 |

`AppData/Local/crash/` 这个空壳 **2026-09-08 16:28:38 就建好了** ——
正是本项目第一次运行的时间,说明这个顺序 bug 从第一天起就在。

叠加的第二个问题:`main.cpp` 原本在 `QApplication` 构造**之前**就
`QMessageBox box; ... box.exec();`。`QMessageBox` 是 `QWidget`,
没有 `QApplication` 实例构造即 abort —— **就算路径对了,弹框自己也会打死进程**。

**为什么 28 天没人发现**:`CrashHandler.cpp` 此前**零测试覆盖** ——
它根本不在 `hmi/tests/CMakeLists.txt` 的 `HMI_CORE_SOURCES` 里。
「写 dump」和「崩了有人知道」是两件事,后者从没被测过。

修法(不是简单调 `main()` 顺序):把 dump 路径改成**纯函数** ——
`GenericDataLocation` + 常量拼接,完全不读 `QCoreApplication` 的全局状态。
**顺序是靠注释约束的,纯函数是靠测试守着的**;只要"调用方什么时候设了什么"
还会漂移,漂移的后果就是崩了却没留下任何可分析的现场。

- org/app 收成 `crash::kOrgName` / `kAppName`,`main.cpp` 也从那儿取
- `main.cpp`:元数据提到最前;弹框挪到 `QApplication` + SingleInstance 之后
  (后者顺带防止**第二实例把主实例该报的崩溃信息吃掉**)
- 新增 `HMI_CRASH_DIR` 覆盖开关:运维收集现场 dump / 测试隔离都用它

⚠ **本次修复中我弄坏的东西,如实记**:新写的 `tst_CrashHandler.cpp` 最初在
`cleanupTestCase` 里写了 `QDir(crash::dumpDirectory()).removeRecursively()`。
上一轮运行 `initTestCase` 的隔离护栏**判红了**,而 Qt **不会**因为
`initTestCase` 失败就跳过 `cleanupTestCase` —— 那句递归删除对着**真实的**
`QianWei/HMI/crash/` 执行,**删掉了现场的 `pending.txt` 与那个 366 KB 的 dump**。
日志、审计、`history.db`、`users.json` 未受影响。

教训:**护栏只保护它自己所在的函数,不够。** 测试不配拥有"递归删除任意路径"
的能力,已整句删除,改用 per-test 的 `init()` 钩子重新锁隔离。

### 测试逮到两个我自己写的假注释

这次特意先写测试再收尾,两条用例直接判红 —— 都不是新代码的错,是**搬过来的注释里有假话**:

1. **已处理行的灰字达不到 WCAG AA。** F3 当年定的 `#787878` 配 `#f0f0f0`

   触发值 —— 操作员事后回看"十分钟前那条确认过没"读的就是这几个字。

2. **注释表里的对比度四行错了三行。** `AlarmRowPalette.cpp` 头部那张表写的是
   `11.6 / 10.1 / 8.3 / 5.34`,实算是 `8.99 / 6.27 / 6.15 / 5.34`,
   最严重的"严重"档虚高了 35%。那些数是"看着挺高"写上去的,没有一个真算过 ——
   而这个文件的全部存在意义就是"别让注释里的对比度变成一句没依据的话"。

   → 新增 `tst_AlarmRowPalette::documentedRatiosAreTrue`,断言的是
   **"注释里写的数 == 实测的数"**(不是"实测 ≥ 某条线")。
   WCAG 用例守住 ≥4.5 的地板,它守住"改了颜色注释不会悄悄变成谎话"。
   它是**有意脆弱**的:颜色一动就红,强制注释和代码两边一起改。

另外把"严重"档亮相的 `#ff9682` 换成 `#ff9b87`:前者色相 9.6°、`QColor::hue()`
取整成 9°,而暗相是 10°,被 `lit_keepsTheSameHueAsDark` 判红。
色相 = 60×(G−B)/(R−B),`#ff9b87` 的 R−B=120、G−B=20 → **精确 10°**,与暗相完全相同。
差 1° 肉眼看不出来,但那条测试守的是"色相不许变" —— 与其把判据放宽成"差 1° 算过",
不如把颜色改成精确保色相。

### TcpClient 重连:"放弃"之后客户端自己又活了(改善清单 #2)

**新开 `tst_TcpClient`** —— `TcpClient` 从阶段 1 起就是核心类，
此前**一个测试文件都没有**，重连/退避/放弃整套逻辑从没被验证过。

Qt 连接失败时的信号顺序是**确定的**：`errorOccurred` 先，`disconnected` 紧跟其后，
两个槽都调 `scheduleReconnect()`。平时靠 `reconnectTimer_->isActive()` 挡住第二条。
但"重试到上限放弃"那条分支**故意没有启动定时器** —— 防护失效了；
那条分支又顺手把 `retryCount_` 清成 0，于是紧接着的 `disconnected`
看到 `retryCount_=0 < 5`，**又排了第 1 次重连**。

后果不是"偶尔多试一次"：**每一轮放弃后都重启，客户端永远停在"重连中"，
界面上"连接失败"一闪而过** —— 恰好是操作员最该看见的那句话。
而且没有任何人按过重连按钮，是它自己活过来的。

改法：加 `reconnectAbandoned_` 标志，置位后 `scheduleReconnect()` 直接返回。
标志由 `connectTo()`（用户手动重连）和 `onSocketConnected()`（连上了）清掉 ——
**不能做成永久状态**，那比原 bug 更严重（机器再也连不上）。

负向对照：去掉守卫后，只有 `abandoned_thenDisconnected_doesNotRestartRetryCycle`
和 `abandoned_emitsAbandonedOnlyOnce` 两条转红（`abandoned.count()` 变成 2 和 4，
正是"放弃 → 重启 → 再放弃"的循环）；
`abandoned_clearedWhenUserConnectsAgain` **保持绿**，证明反向没被误伤。

### 改善清单 #10 复核结论：这条清单是错的，照做会让程序变慢

清单原话"`setSocketOption` 每次都设 → 移到构造"，听起来是纯粹的清理。实测不是：
在**未连接**的 `QTcpSocket` 上设 `LowDelayOption` 是 **no-op**，Qt 直接丢弃这个请求。

维持原样，并在构造函数处写了长注释防止下一轮再被"优化"回去。
`lowDelayOption_mustBeSetAfterConnect` 用两个**与 TcpClient 无关的裸 socket 探针**
隔离验证（第一次想直接在 TcpClient 上断言，被自己先红了一次：

### F6 区域过滤 —— 卡了很久,因为它不是界面活,是改工程文件格式的决定

Wqian 拍板:**手填自由文本 + 已用过的值做补全**。三个选项里

三条理由：

1. **不复用 `plcId`** —— 它是**通信归属**不是**组织归属**。
   一台 PLC 常同时带一号泵房和二号泵房，一个区域也可能横跨两台 PLC。
   **一个经常筛错的筛选框比没有更糟。**
2. **不做工程级区域清单** —— 自由文本是清单方案的**真子集**：
   现在只多一列 `TEXT`，将来想收窄成下拉清单只改 UI 不动 schema；
   反过来先做清单、日后发现多数项目只有两三个区域，就得迁移第二次。

**一个筛选器如果能把用户引向错误的结论，那它比没有这个功能更糟。**

追加在**末尾**（插中间会让按列号取值的老脚本串列），

### F3-b 运行时画布的报警列表会闪了 —— 并且抓到一句我自己写的假注释

`repaintRow()` 里我先写的是亮红 `#f05a5a` 配白字,注释还特意标了"保证对比度不降"。
拿 WCAG 相对亮度公式算了一遍,发现**那句话是假的**:

| | 底色 | 字色 | 对比度 |
|---|---|---|---|
| 危急 暗相(原) | `#cd2828` | 白 | 5.34:1 |
| 危急 亮相(**原写法**) | `#f05a5a` | 白 | **3.33:1** ← 掉了一截 |
| 危急 亮相(改后) | `#f05a5a` | `#3b0606` | 5.20:1 |
| 严重 亮相 | `#ff9682` | `#780a05` | 5.39:1 |

即**闪烁最亮的那半拍恰恰是字最难读的那半拍** —— 而那正是操作员最想看清
"哪条报警、多严重"的时候。根因是底色一提亮白字必然失效,两者不能同时要。

**所以这句话不能只留在注释里。** 注释是写给我自己看的,下一次调色的人未必会重算;
而"字看得清"和"底色够亮"在屏幕上长得完全一样,没人会拿两个色块数字去比。
→ 新增 `blink_textStaysReadableInBothPhases`,断言两个相位下对比度都 ≥ 4.5:1
(WCAG AA 正文最低要求),并用变异验证:字色改回白字,该用例立刻红并报出 3.33:1。

代价如实记:危急在亮相半拍不是白字了(「唯一用白字的档」只对静止态成立)。
取舍是"看得清"优先于"用白字标识最重的那一档"—— 后者只是约定,前者是能不能读。

**测试写法**:5 条新用例全部用 `advanceBlinkForTest()` 手动走相位,

**三件写下来才想明白的事**

1. **"等级"那一栏必须写"最低等级: 严重及以上",不能写"等级 = 严重"。**

2. **最新的排在最上面,但改的是视图不是 query。**

   (事故分析从头顺着读下来最顺)。但操作员点开"报警历史"是想看"刚才发生了什么",

### F2-c 报警屏蔽(shelve)—— 让"这条报警现在没意义"能被按掉,而且必须看得见

**加了什么**

- `AlarmManager` 新增 `shelve / unshelve / isShelved / shelveCount / shelvedNames`,
  外加 `shelveChanged(name, bool)` 信号。屏蔽收口在 `onCheckerTriggered` ——
  所有 checker 报警的唯一入口,所以阈值报警、写失败报警等**所有类别**一致受管。
  (放进各个 Checker 里就只有阈值报警能被屏蔽。)
- `clearAll()` 顺带清空屏蔽名单,换工程不会带着上个工程的静默名单开局。
- 新增 `tst_AlarmShelve`(9 个用例)。

**为什么把"可见"当成硬约束**

如果"被屏蔽的 checker 不触发"是唯一表现,那就是:屏幕上没有行、没有计数、
没有日志 —— 操作员会以为"这次真没报警",实际是**被我们藏起来了**。
更糟的是检修结束忘了取消屏蔽 → 传感器真的坏了 → 依然没有报警。
设备坏了而界面一片安静,这是能出人命的。所以三条硬约束:
`shelveCount()` 随时可查、`shelveChanged` 让界面自己跳出来、屏蔽必须能撤销。

**没做的:自动到期**。工业上常见"屏蔽 8 小时自动恢复",本次不做 ——
它需要常驻定时器 + 到期语义 + 跨重启策略,而当前项目连报警编辑 UI 都还没有
(配置只能手改 JSON)。宁可少做一半,也不做出一个"以为会自己恢复、实际不会"的半成品。

**屏蔽的是"进不进系统",不是"检测器还测不测"**

拦截点在 Manager,`ThresholdAlarmChecker` 照常在算、传感器照常在越线。
这条不能含糊:调试时看到"检测器还在报但界面没反应"是正常的,
反过来若把检测也停了,故障就彻底不可见了。

| 已注册、状态未变 | `true`,不重复计数 | `true`,no-op 不发信号 |

**证据**(反向验证,不是"改完看着对了")

### F2 报警滞回 —— 治 chatter,并且先纠正一个我自己的误判

**加了什么**

- `CheckerConfig` 新增 `hysteresis` 字段(默认 `0.0` = 不启用),`JsonSerializer`
  读写 `hysteresis` 键。老工程文件没这个键 → 回落 `0.0`,行为与 5.3 完全一致。
- `ThresholdAlarmChecker` 状态机从 `bool active_` 改成显式三态
  `Idle / Pending / Fired`。滞回只在 `Fired` 档生效:报警已报出后,必须跌到
  `threshold - hysteresis` 才算恢复,值在死区里来回摆不再反复"恢复→再触发"。
- 新增 `tst_ThresholdAlarmChecker`(8 个用例)—— 这是**该文件第一次有测试**。
  `minDurationMs` 防抖逻辑此前从来没被任何一条用例执行过。

**我自己的误判,记在这里别删**

我最初判断"`active_` 同时表示待触发和已触发 → 报警恢复后再超限会【重报同一条报警】,
这是 bug",还把它立成任务 #14。**拿修复前的代码跑测试,那条断言是绿的** ——
它描述的是原有行为,不是缺陷。

真实结论:**高 → 正常 → 再高报两次是正确的工业语义**。两次就是两次独立工况,
操作员需要知道"它又犯了一次"。该压掉的只有 chatter:模拟量在阈值附近来回摆,
每次越线都超过 `minDurationMs`,于是形成一串完整的 触发→恢复→触发。

三态重构仍然保留 —— 因为单 bool 确实区分不了"待触发"和"已触发",
滞回没法只挂在 `Fired` 这一档上。但它是**为滞回铺路的重构,不是 bug 修复**,
这两者的区别不该含糊。

**证据**(反向验证,不是"改完看着对了"就交)

| 用例 | 修复前 | 修复后 |
|---|---|---|
| `chatter_slowOscillation_isSuppressedByHysteresis` | **红**(4 次触发 / 期望 1) | 绿 |
| `hysteresis_valueInDeadBand_doesNotRecover` | **红**(死区内就报了恢复) | 绿 |
| 其余 6 条 | 绿 | 绿 |

chatter 用例里 A 组(无滞回)断言 `4 次触发 + 4 次恢复` —— 这条是**在修复前就成立**的,
它先把"抖动确实会刷屏"这个事实钉住,再由 B 组(加滞回 → 1 次)对照。

**顺带记录一个滞回的边界**:低点必须**留在死区内**才有效果。
`threshold=50, hyst=10` 时死区是 `(40, 60)`,低点若跌到 30(< 40)已越过恢复沿,
照样每次都报。我第一版用例把低点写成 30,测试红着才发现 —— 边界值得写进用例。

### 阶段 E · 收口后补的两件用户路径缺口

#### 2. E.7 复制 / 粘贴 / 删除（`35fc787`）

编辑器此前**只能加控件** —— 选中一个元件按 Delete 没有任何反应,也不能复制粘贴。

**为什么命令存 JSON 快照而不是 `ControlBase*`**：
`GeometryChangeCommand.h` 早就写明"QUndoCommand 被 delete 时控件可能已经没了"。
删除类命令更狠 —— 撤销一次删除,`undo()` 造的是一个**新对象**,
所有旧指针当场变悬空指针。所以 `ControlListCommand` 只存 `QList<QJsonObject>`,
把命令和控件的生命周期彻底解开。

**快照必须用 `propertiesToJson()` + `registryKeyFor()`,不能用 `toJson()`**：
后者写的 `type` 是类名 `"RectangleControl"`,而 `create()` 查的是注册表短名 `"Rectangle"`。
对不上就**静默返回 nullptr**,画面凭空少一块且零报错 —— 这正是 E.5 踩过的坑,
`tst_ControlClipboard::copy_snapshotType_isRegistryShortName_notClassName` 专门守它。

**增删合一**:`forPaste` / `forDelete` 两个工厂,内部同一个 `Kind` 枚举。
两者 undo/redo 逻辑完全一样,只有"首次 redo 是不是空操作"不同,
拆成两个类等于把快照/销毁/选中逻辑写两遍。

**顺带修掉 3 个真 bug**：
1. **粘贴首贴不偏移** —— offset 乘的是 `pasteCount_`(首次为 0),第一份会严丝合缝压在原件上,
   用户看着像没生效。改成乘 `pasteCount_ + 1`。
2. **撤销删除后控件层级整个翻转** —— `targets_` 来自 `selectedItems()`,Qt 给的是**按叠放序倒序**。
   照抄这个顺序重建,画面上的前后关系跟删之前不一样。改成按 `controls_` 原始顺序重排。
3. **`destroyControl` 缺 `setSelected(false)`** —— `QGraphicsScene` 内部拿**裸指针**记着选中项,
   直接 `removeItem` + `delete` 会留一个指向已释放内存的指针在 scene 里。

**测试** `tst_ControlClipboard` 25 用例,重点是「删→撤→删→撤」连环 5 轮 ——
命令存快照,撤销造新对象,旧指针当场失效,残留一处在第二轮就出事。

#### 4. B 组 4 张 bug 现场图 —— 复现 + 修复（多选时位置框永远置灰）

`docs/bug图/README.md` 里挂了两个月"疑似遗留未修"的 4 张图(图2/图3/图6/图7),
2026-09-30 复现成功。**一个根因,不是四个。**

`PropertySheet::rebuildForm` 判断"多选是否同值"时拿的是**整个属性值**:

```cpp
if (other->property(prop.name()) != firstVal) { common = false; }
```

`position` 是 `QPointF`、`size` 是 `QSizeF` —— 比的是整个点/整个矩形。
两个控件只要有**任一分量**不同,整个复合编辑器就被 `setEnabled(false)` 置灰。

**为什么在多选时是致命的**:多选时 `position` 几乎**必然**不同值(不然就不叫多选了),
于是属性面板的位置框**永远灰着、永远看不了**。用户选了 3 个控件想看它们各自在哪,
面板只给一个灰掉的 `0.00`。

而 `0.00` 恰恰是**症状的放大器**:异值时 editor 被置空,`QDoubleSpinBox` 读回来是默认值 0。
用户看到 `x = 0.00` 会以为控件真跑到原点了,于是怀疑框算错、handle 错位 ——
图上那些"红框和控件错位"的观感就是这么来的。**框没算错,是面板在装死,还装得像报了个坐标。**

**改动**:
1. `PositionEditor` / `SizeEditor` 加按分量的接口(enabled / valid 分离)
2. `PropertySheet` 改成**按分量分别判同值**:`x` 相同就照常显示可编辑,只有真不同的那格才灰
3. 顺带修掉一个连带的坑 —— 异值那格被置空成 0,改另一格时 `onXChanged` 把这个
   **0 当真值**发出去,`applyEditorChange` 写进所有控件 → **改 x 把所有 y 刷成 0**。
   现在用 NaN 标记"该分量别动",写入侧跳过
4. `syncFormFromTarget` 同步改成分量级刷新(否则属性变更后灰度不更新)

**测试** `tst_PropertySheet` 新增 3 条:
- `multiSelect_positionNotAllZero` —— 两分量都不同 → 都该灰(别把"该灰"改成"不灰")
- `multiSelect_positionPartialCommon` —— x 同 y 异 → x 可编辑显示 10;改 x 后 y 各归各不被刷成 0
- `multiSelect_sizePartialCommon` —— size 分支同样按分量(图2 的 width/height 0.00)

`ctest` **57/57 全绿**,`hmi.exe` 构建通过。

#### 5. E.8 控件自定义底图 —— 22 个控件手绘太丑

Wqian:"这些元件的图片都太丑了,有没有那种自定义背景图片的功能"。

**为什么是"底图叠加"而不是"换掉手绘"**：泵的转子旋转、罐的液位、阀的开合
**本身就是功能**,不是装饰。换成一张静态图,储罐的液位就永远不动了。
所以图走**下层**,22 个控件的矢量层(液位/动画/状态色)**一律保留在上层**。

**改动 1:能力下沉到基类,一个文件覆盖 22 个控件**

`ControlBase` 原本是 `virtual void paint() = 0`(每个控件自己画全部)。
改成**模板方法**：

```cpp
void ControlBase::paint(...) override final {      // 终态,派生类改不了
    if (ensureImageLoaded() && !cachedPixmap_.isNull()) { /* 画底图 */ }
    paintContent(painter, option, widget);         // 纯虚,各控件自己的矢量层
}
virtual void paintContent(...) = 0;                // 22 个控件只需改函数名
```

22 个控件的改动是**纯机械改名** `paint` → `paintContent`(22 个 .h + 22 个 .cpp),
新增的底图逻辑一行都不用碰它们。**这是选基类而不是逐个控件加属性的全部理由。**

**改动 2:`ImageControl` 的属性被删掉了,不是"重复定义"**

`ImageControl` 原本**自己就有** `imagePath` / `scaleToFit`。
基类加上同名属性后,一个类上会出现两个同名 `Q_PROPERTY` ——
哪个生效取决于 Qt 元对象的继承顺序,反射和序列化行为会变得不可预测。
所以把 `ImageControl` 自己的两个属性**删干净**,只保留"没配图时画个占位框"。
**两个真值来源 = 迟早有一次不匹配。**

**改动 3:相对路径,不存绝对路径**

存绝对路径 = 把刚修掉的 `tst_ProjectSchema` 硬编码 `E:/qianwie/...` 那个错
复制到产品代码里 —— 工程文件拷给同事、换个盘符,底图全丢。
所以存**相对工程文件目录**的路径,`basePath` 从 `EditorMainWindow` / `RuntimeCanvas`
一路传到 `ControlBase`。

顺带一个坑:**pixmap 缓存的判据是解析后的绝对路径,不是 `imagePath_` 属性值**。
按属性值判的话,`basePath_` 变了(打开另一个工程)而属性没变时会命中旧缓存 ——
画面上挂着的是上一个工程的图。`basePathChange_invalidatesCache` 专门守这条。

**改动 4:加载失败回退手绘,不是画灰底**

图没了(文件被删/路径错)如果画一片灰,用户看到的是"设了没反应",
和"图加载了但太暗"分不清。所以**直接不画底图、矢量层照旧**,
`qWarning` 打出来,属性面板那个输入框**描红边 + tooltip 提示**。

**属性面板**:输入框 + `[浏览…]` + `[清除]`。

##### 6.1 报错不含变量名、不含字段、两种错报同一句话

`data_type` 写成小写 `int16`、漏写 `access`、缺 `name` —— 三种完全不同的错，

```
第 6 个 variable 解析失败:
变量 "Boom": "data_type" = "int16" 不合法
  合法值:Bool, Int16, UInt16, Int32, Float（注意大小写,小写 int16 无效）
```

> 合法值是 `keyCount()/valueToKey(i)` 现场拼的 —— `QMetaEnum` 没有 `keys()` 成员。
> 写死一份枚举名列表的话，加新类型时它会静静过期，变成第二种静默失败。

（新版本加的字段被老版本读到时，不该直接拒绝加载整个工程）。

`clear()` 只在 `loadRootFromFile` 开头调一次，而下面 5 个解析循环各有 `return false`
—— 走到那里时前 N 个变量/报警已经建出来了。调用方若不检查返回值直接继续用，
就拿到了残缺状态。

收成一个 `failWith()` lambda 统一清。**抽 lambda 不是为了省那 3 行**，是为了
