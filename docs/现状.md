## 三、分层架构(7 层 + v0.2.0 新增子层)

```
UI(hmi)              ┐  3 个状态机 State/ConnState/ModbusState,唯一出口 updateUi()
业务协调(AlarmManager / ActionManager) │
业务执行(ThresholdAlarmChecker / WriteFailChecker) ├─ Qt signal/slot 是唯一调度机制
调度(PollScheduler / WriteScheduler) │  100ms tick,唯一的"主动推"
协议(IPollDriver 抽象 → ModbusDriver / S7Driver / EipDriver) │  v0.2.0 C 阶段抽象层
传输(TcpClient)      │  连接/指数退避重连/心跳
数据(Variable / VariableManager) │  tag/value/quality/deadband/range/dirty
配置(Project / JsonSerializer) ┘  JSON 存读

=== v0.2.0 新增的旁路子系统(走信号槽,不影响 7 层主轴) ===
A 阶段:logging/  crash/  instance/  tray/
B 阶段:auth/(UserStore / UserManager / PasswordHasher / AuditLog / LoginDialog / ...)
D 阶段:history/(SQLite) / export/(CsvExporter) / tag/(ExpressionParser / TagImporter)
E 阶段:widgets/(22 控件) + editor/(PaletteWidget / EditorMainWindow / PropertySheet / GeometryChangeCommand / ControlListCommand / RuntimeCanvas / ...)
```

**关键事实**:全部 7 层都在**主线程**,没有 QThread / QtConcurrent,emit/slot 同步触发。
唯一的主动驱动是 Poll/WriteScheduler 的 100ms tick + 历史库 60s 心跳 tick,其余都是被动响应。

详细的 5 条流程(启动/读/写/报警/存读)见 `docs/专题/2026-08-09_调度机制.md`。
E 阶段编辑器架构见 `src/editor/EditorMainWindow.h`。

## 四、两条数据流(项目灵魂)

**读(PLC → UI)**
`PollScheduler::onTick`(100ms)→ 挑到期变量 + 合并连续地址 → `ModbusMaster` 组帧 →
`TcpClient` 发出 → 响应回来拆帧 → `Variable::setValue` → `emit valueChanged` →
`Binding` 刷新 QLabel。**并行通道**:`emit rawRead` → 报警检查(绕开死区过滤)。

**写(UI → PLC)**
用户在 QLineEdit 回车 → `Binding::bindEdit` 校验 → `setValue` + `markDirty` →
`WriteScheduler::onTick` 扫 dirty → 发 Modbus 写 → `writeFinished` → `clearDirty` + 审计日志。
失败保留 dirty 下帧重试,超过 `kMaxWriteRetries`(3)→ `emit writeFailed` → 报警。

## 五、写代码必守约定

1. **事实 → UI 单向流**:业务只改 `state_ / connState_ / modbusState_` 等"事实",再调 `updateUi()`。
   **绝不在槽函数里直接 `setText`。**
2. **信号转发链分层**:`QTcpSocket → TcpClient → hmi`,上层不认识底层 socket。
3. **加新 `.cpp/.h` 第一步必须同步 `hmi.vcxproj` + `hmi.vcxproj.filters`**

5. **持有裸 `Variable*` 的模块必须 connect `VariableManager::variableReplaced`**,
   否则 loadFromFile 后是悬空指针。原因见 `docs/专题/2026-08-27_ActionManager报警联动与悬空指针.md`。
6. 注释格式:`★ IMPROVE-x.y(日期)` + `【背景】【改法】【取舍】【参照】`。
7. 改动源码需 Wqian 同意;改工作区文件需当条消息显式授权。

### ⚠ VS 2026 的 ucrt 坑(必读,别再踩)

VS 2026 v18 的 `vcvars64.bat` 只把 `um/shared/winrt/cppwinrt` 加进 INCLUDE,
**漏了 `ucrt`** → 报 `error C1083: 无法打开包括文件: "stddef.h"`。

**两条无效解**(别浪费时间):
- `set INCLUDE=...;%INCLUDE%` —— MSBuild 会重置 env,不生效
- `/p:IncludePath="ucrt;$(IncludePath)"` —— 编译过但 link 找不到 `kernel32.lib`
  (此时 `$(LibraryPath)` 还没被 props 赋值,被整体替换成只剩 UCRT)

**真稳修法** —— 改 `hmi.vcxproj.user`(VS 标准用户级覆盖,不污染 vcxproj / git):

```xml
<PropertyGroup>
  <IncludePath>$(IncludePath);C:\Program Files (x86)\Windows Kits\10\Include\10.0.26100.0\ucrt</IncludePath>
  <LibraryPath>$(LibraryPath);C:\Program Files (x86)\Windows Kits\10\Lib\10.0.26100.0\ucrt\x64</LibraryPath>
</PropertyGroup>
```

这两个属性在 props sheet 设置**之后**追加,VS IDE 和命令行都生效。


#### F1:报警历史存出孤儿行(已修)

`AlarmManager::onCheckerRecovered` 的顺序是 **erase → emit**:

```cpp
it->recoveredAt = now();
activeAlarms_.erase(it);        // ← 记录没了
emit alarmRecovered(id);        // ← 只传 id
```

而 `AlarmRecorder::onAlarmRecovered` 靠**遍历 `activeAlarms()`** 取完整数据 ——
刚 erase 的那条**必然遍历不到**,直接走兜底 `insertAction(id, {}, 0, ...)`。

**结果:历史表里每一条"恢复"行的 `name`/`level`/`variable_name`/`trigger_value`/`threshold` 全空。**
事故追溯查出来是一行只有 id 和时间的孤儿。

**为什么两个月没人发现:** 旧测试 `recordRecovered_writesActionTwo` 只断言
`action==2 && id 匹配` —— 恰好是这条路径上**唯一没坏的两样**。
断言挑在了不会红的地方。

**修法**(不只是调顺序):

1. 恢复的记录进 `archived_`(有界 500 条)而非直接销毁 —— 只调顺序的话
   `acknowledgedAt`/`state` 照样当场蒸发,「没来得及确认值就回来了」这种

### F2 报警滞回(2026-09-30 滞回部分已完成 · 屏蔽/shelve 未做)

**`ThresholdAlarmChecker` 此前零测试覆盖。** 全仓检索,它在测试里一次都没出现过 ——
只存在于 CMakeLists 和别的测试「这里故意不用它」的注释里。
也就是说 `minDurationMs` 这段防抖逻辑**从来没被任何一条用例执行过**。
先补测试再改逻辑,顺序不能反。

#### 我自己的一处误判(已纠正,别再犯)

开工时判断:`active_` 一个 bool 同时表示「待触发」和「已触发」,
所以报警恢复后再超限会**重报同一条报警** —— 记成了 bug,立了任务 #14。

**拿修复前的代码跑,那条断言是绿的。** 它描述的是原有行为,不是缺陷。

真实结论:**高 → 正常 → 再高报两次是正确的工业语义** —— 两次就是两次独立工况,
操作员需要知道"它又犯了一次"。压错了报警,比多报一条危险得多。

该压掉的只有 **chatter**:模拟量在阈值附近来回摆,且**每次越线都超过
`minDurationMs`**(所以防抖挡不住),形成一串完整的 触发→恢复→触发。
用例把这点钉住了:无滞回时 4 轮摆动 = **4 次触发 + 4 次恢复**。

#### 改了什么

- `CheckerConfig` 加 `hysteresis`(默认 `0.0` = 不启用),`JsonSerializer` 读写
  `hysteresis` 键。老工程没这个键 → 回落 0,**行为与 5.3 逐位相同**。
- 状态机 `bool active_` → 显式三态 `Idle / Pending / Fired`。
  滞回**只在 `Fired` 档生效**:已报警后须跌到 `threshold ∓ hysteresis` 才算恢复。
  这是保留三态的真正理由 —— 单 bool 区分不了「待触发」和「已触发」,
  滞回没地方挂。**但这是为滞回铺路的重构,不是 bug 修复**,两者别混为一谈。

#### 反向验证(不是"改完看着对了")

| 用例 | 修复前 | 修复后 |
|---|---|---|
| `chatter_slowOscillation_isSuppressedByHysteresis` | **红**(4 次触发 / 期望 1) | 绿 |
| `hysteresis_valueInDeadBand_doesNotRecover` | **红**(死区内就报了恢复) | 绿 |
| 其余 6 条 | 绿 | 绿 |

> **滞回的边界(踩过一次)**:低点必须**留在死区内**才生效。
> `threshold=50, hyst=10` → 死区 `(40, 60)`;低点若跌到 30(< 40)已越过恢复沿,
> 照样每次都报。用例第一版把低点写成 30,测试红着才发现。

### F2-c 报警屏蔽(shelve)✅ 2026-09-30 完成

滞回压的是"报太多";屏蔽解决另一类:**"这条报警现在没意义,别烦我"** ——
传感器检修中、某台泵本来不投用,它的报警纯属噪声。

**放在 `AlarmManager` 而不是 Checker**,三个理由:

1. `onCheckerTriggered` 是所有 checker 报警的**唯一收口点** → 阈值报警、
   写失败报警等**所有类别**一致受管(放 Checker 里就只有阈值报警能被屏蔽);
2. 状态可查 / 可撤销 / 可枚举(界面据此显示"N 条被屏蔽");
3. `clearAll()` 一次清干净,换工程不会带着上个工程的静默名单开局。

**静默屏蔽比不屏蔽更危险 —— 这是本功能的硬约束**

若"被屏蔽的 checker 不触发"是唯一表现,屏幕上就没有行、没有计数、没有日志,
操作员会以为"这次真没报警",实际是**被我们藏起来了**。更糟的是检修结束忘了
取消屏蔽 → 传感器真的坏了 → 依然没有报警。**设备坏了而界面一片安静,这是能出人命的。**
所以三条硬约束:`shelveCount()` 随时可查 / `shelveChanged` 让界面自己跳出来 /
屏蔽必须能撤销(不是单向门)。

**屏蔽的是"进不进系统",不是"检测器还测不测"**

拦截在 Manager 层,`ThresholdAlarmChecker` 照常在算、传感器照常在越线。
调试时看到"检测器还在报但界面没反应"是正常的;反过来若连检测一起停,
故障就彻底不可见了 —— 那比多报一条危险得多。

**没做:自动到期。** 工业上常见"屏蔽 8 小时自动恢复",本次不做 ——
需要常驻定时器 + 到期语义 + 跨重启策略,而项目连报警编辑 UI 都还没有(配置只能手改 JSON)。
宁可只落"手动可撤销"这一半,也不做出一个"以为会自己恢复、实际不会"的半成品。

#### 反向验证

把 `onCheckerTriggered` 的拦截条件改成 `false &&` 重跑:

### F4 报警历史查询(2026-10-08)· 存了三个月的历史,终于看得见

D.3 把报警落库做完了,主窗口的"报警历史"tab 却一直是个占位 Label ——
**存了但看不见的历史等于没有历史**。出了事故要复盘,连"昨晚到底报了什么"都答不上来。

现在能按**时间范围**(手选 + 1 小时/24 小时/3 天/7 天快捷)和**等级**查了,
**最新的排在最上面**,0 条时明确说"该条件下没有记录"而不是留一张空表。

**三件写下来才想明白的事:**

**1) 那一栏必须写"最低等级: 严重及以上",不能写"等级 = 严重"。**
`AlarmRecorder::query` 的第三个参数是 `minLevel`,它是**下限**不是集合,
选"严重及以上"会把危急一起带出来。界面上写"等级 = 严重"的话,
用户看到危急的记录不见了,会去查"危急报警是不是没记录" —— 而它好好地在库里。
**这是界面在撒谎,比缺功能更糟。**

**2) 最新的排在最上面,但改的是视图不是 query。**
`AlarmRecorder::query` 是 `ORDER BY action_at ASC`,那是**导出 CSV** 要的顺序
(事故分析从头顺着读下来最顺)。但操作员点开"报警历史"是想看"刚才发生了什么",
让他自己翻到最后一行去找,等于没有这个界面。
两种顺序各有各的用处,改全局会连 CSV 导出和现有测试一起改掉,
所以 `std::reverse` 放在表现层 —— 同一份数据,**给人看的倒着排,给机器读的顺着排**。

**3) 等级和动作两列全是乱码,一条用例绊出来的。**
报错打印 Actual 是 `ä¸¥` —— 肉眼看过去**就是"严重"两个字的乱码形状**,
很容易以为是自己期望值写错了。真病根在实现:显示用的字面量是源码里的 UTF-8,
代码却用 `fromLatin1` 转,"严"的 3 个字节 `E4 B8 A5` 被当成 3 个 Latin-1 字符。
名字那一列一直是对的(直接从库里取的 QString),
**正是这种"别的列好好的、就这两列是乱码",最容易让人以为是数据问题。**

### F6 区域过滤(2026-10-10 · Wqian 拍板)

**这一条卡了很久,因为它不是界面活,是【改工程文件格式】的决定。**
当时整个代码库里没有"区域"这个概念 —— `Alarm` 结构里没这个字段,工程文件里也没有。

三条理由(完整版留档在 `src/history/AlarmHistoryView.h`):

1. **不复用 `plcId`** —— `plcId` 是**通信归属**不是**组织归属**。

   `plcId` 经常不是一个正确的区域,**一个经常筛错的筛选框比没有更糟**。
2. **不做工程级区域清单** —— 自由文本是清单方案的**真子集**:
   现在只多一列 `TEXT`,将来想收窄成下拉清单只改 UI 不动 schema;
   反过来先做清单、日后发现多数项目只有两三个区域,就得迁移第二次。
3. **老库迁移不再是障碍** —— F2 已建好探测式加列(`AlarmRecorder::addColumnIfMissing`)。

落地链路:`Alarm.area` / `CheckerConfig.area` → JSON(`JsonSerializer`)→
`ThresholdAlarmChecker` 发出时带上 → `AlarmRecorder` 落库(11 列)→
`AlarmHistoryView` 下拉筛选 → `AlarmConfigDialog` 表格 + 可编辑下拉 → `CsvExporter` 导出。

**★ 落地时冒出来的一个额外要求(原始设计里没有)**
老库里**全部**记录的 `area` 都是 NULL。用户第一次用新版本,选"一号泵房"→ 0 行 →
他会得出"报警历史丢了"的结论,而真相是记录都在、只是没区域可分。
**一个筛选器如果能把用户引向错误的结论,那它比没有这个功能更糟。**
所以下拉里必须有"未分配"这一项,而且必须真的能筛出来 ——
区分靠 QString 的 **null(不筛)/ 空串(筛未分配)**。

**★ 途中踩到一个真实的 Qt 坑:`QVariant` 把 null 和空串判成相等。**
最初把区域值放在 `QComboBox::itemData` 里,`findData("")` 命中了索引 0 那项
"全部"(它的 data 是 `QString()`,null) —— **"筛未分配"静默退化成了"不筛"**。
界面看不出任何异常,筛选框也照样能选。改成旁路一份 `QStringList areaValues_`(不过 `QVariant`),
并在 `reloadAreaCombo` / `selectedArea` / `setAreaFilter` 里一律显式 `isNull()` 比较。
这个坑是**测试逼出来的**:`areaFilter_unassignedBucketIsReachable` 期望 1 行、实得 2 行。

**负向对照**(拆掉实现重跑,红的**且仅是**该红的):
`COALESCE` 去掉 → 只红 1 条;`unassigned()` 返回 null → 只红同一条;
`insertAction` 不绑 area → 红 4 条;对话框导出丢 `cfg.area` → 红 2 条;
去掉 `.trimmed()` → 只红 1 条;CSV 少 `area` 列 → 红 3 条,原有 4 条 CSV 用例**仍绿**。

验证:`ctest` **66/66 通过**、`hmi.exe` 编译通过。

### F5 报警声音 / 蜂鸣(2026-10-08)

### F3-b 运行时画布的报警列表会闪了(2026-10-08)· 但也踩中了一个"我自己写的注释是假的"

补的是第七节那条 🟡 的前半截:运行时画布上的 `AlarmListControl` 原来**根本不闪**,
而 E.5 之后操作员实际盯的是运行时画布 —— 也就是"会闪的那套"不在他眼前。

- **速度对齐 500ms**,取主画面 `hmi.cpp:423` 的同一个值。两套 UI 各闪各的、
  速度还不一样,操作员目光在两者间来回会觉得"这边快了一点"。
- **判据对齐** `hmi.cpp:1492`:未确认 + 严重/危急。
  信息/警告闪 = 现场最吵的永远在闪,真出事的那条被淹了;
  已确认的还闪 = 骗操作员去处理一条已经处理过的。
- **定时器必须会停**:有该闪的行才开表,一个都没有就停,而且停之前把相位复位。
  这是 7×24 的工控机,没报警时让事件循环一直醒着是纯浪费。
- **相位复位是有理由的**:不复位的话,下一轮启动的第一帧是暗相,
  而那一行的颜色可能还停在亮相的深色上 —— 用户看到"新报警颜色不对,过一会儿才对"。

#### ★ 关键设计:闪的是【亮度】,不是【换一套颜色】

主画面 `hmi.cpp` 闪的时候直接换成 `QColor(255,80,80)` / `QColor(255,200,100)`。
**F3-b 没跟**:那样写的话危急/严重/警告会共用一个红 ——
而"哪一档"正是颜色在表达的信息,操作员靠它分轻重,闪一下就分不出来了,闪烁反而害事。

于是定为:**闪烁 = 本档底色变亮/变暗,色相不变**。
闪 = 在说"这条还没处理";颜色深浅 = 在说"这条有多重"。两件事各走各的通道。
所有改颜色的地方仍然只有 `repaintRow()` 一个(闪烁也走它),
两处各配一次色必然出现"闪一下之后颜色停在错误档位"这类 bug。

#### ★ 这里我写了一句假注释,然后用 WCAG 算出来打自己的脸

`repaintRow()` 里最初写的是亮红 `#f05a5a` 配白字,注释还特意标了
"保证对比度不降"。**那句话是假的。** 拿 WCAG 相对亮度公式算:

| | 底色 | 字色 | 对比度 |
|---|---|---|---|
| 危急 暗相(原来) | `#cd2828` | 白 | **5.34:1** |
| 危急 亮相(原写法) | `#f05a5a` | 白 | **3.33:1** ← 掉了一截 |
| 危急 亮相(改成) | `#f05a5a` | `#3b0606` | **5.20:1** |
| 严重 暗相 | `#ffcdc3` | `#96140a` | 6.15:1 |
| 严重 亮相 | `#ff9b87` | `#780a05` | 5.58:1 |

> ⚠ 2026-10-14 更正:这一行原来写的是 `#ff9682` / 5.39:1,
> 且"严重 暗相"的字色误抄成了亮相的字色。`#ff9b87` 是 2026-10-14 抽公共层时
> 换掉的 —— 原因是色相精确 10°,与暗相同(详见 G-1 一节)。
> 表里每一个数现在都由 `tst_AlarmRowPalette::documentedRatiosAreTrue` 钉住。

即:**闪烁最亮的那半拍,恰恰是字最难读的那半拍** —— 而那正是操作员
最想看清"哪条报警、多严重"的时候。根因是底色一提亮白字必然失效,
两者不能同时要;解法是**亮底配深字**,亮度还能比暗相亮 81%(余光绝对抓得到)。

**这条必须变成测试,不能只留注释。** 注释是写给我自己看的,下一次调色的人未必会重算;
而"字看得清"和"底色够亮"在屏幕上长得完全不一样,没人会拿两个色块数字去比。
→ `tst_AlarmListControl::blink_textStaysReadableInBothPhases`,阈值 4.5:1
(WCAG AA 对正文的最低要求)。已用变异验证:把字色改回白字,该用例立刻红,
并报出 `Emergency 亮相对比度只有 3.33:1`。

**代价要说清楚**:危急在亮相那半拍不是白字了(`styleFor` 里"唯一用白字的档"只对静止态成立)。
取舍理由是"看得清"优先于"用白字标识最重的那一档" —— 后者只是个约定,前者是能不能读。

#### 测试写法:为什么不睡 500ms

5 条新用例全部用 `advanceBlinkForTest()` 手动走相位,**没有一条 `QTest::qWait(500)`**。
"睡 500ms 再看一眼颜色"既慢又不稳:CI 上一旦机器忙,500ms 里定时器可能没被派发,
断言就会随机红 —— 而红的原因和被测逻辑毫无关系。

两条变异都实测过(改前是绿的):

| 变异 | 结果 |
|---|---|
| 亮相不上色(`blinkOn_ && false`) | 2 条红:`dark != lit` / `critLit != critDark` |
| 亮红配白字(最初那版) | 1 条红,报出 3.33:1 这个具体数字 |

#### ★ 抽公共层时,测试逮到两个我自己写的假注释

这次特意先写测试再收尾,结果两条用例直接判红 —— 都不是新代码的错,
是**搬过来的注释里有假话**:

1. **已处理行的灰字达不到 WCAG AA。** F3 当年定的 `#787878` 配 `#f0f0f0`
   只有 **3.87:1**,AA 线是 4.5:1。这一档不是装饰,它上面写着报警名、
   触发时间、触发值 —— 操作员事后回看"十分钟前那条确认过没"读的就是这几个字。
   压到 `#696969` 之后 4.82:1,层级关系没变(在用的四档都 ≥5.2:1 且带饱和底色)。
2. **注释表里的对比度四行错了三行。** 写在 `AlarmRowPalette.cpp` 头部的那张表是
   `11.6 / 10.1 / 8.3 / 5.34`,拿 WCAG 公式实算是 `8.99 / 6.27 / 6.15 / 5.34`,
   最严重的"严重"档虚高了 35%。那些数是"看着挺高"写上去的,没有一个真算过 ——
   而这个文件的全部存在意义就是"别让注释里的对比度变成一句没依据的话"。

   → 新增 `tst_AlarmRowPalette::documentedRatiosAreTrue`,断言的是
   **"注释里写的数 == 实测的数"**(不是"实测 ≥ 某条线")。
   上一条 WCAG 用例守住 ≥4.5 的地板,这一条守住"改了颜色注释不会悄悄变成谎话"。
   它是**有意脆弱**的:颜色一动就红,强制注释和代码两边一起改。

另外把"严重"档亮相的 `#ff9682` 换成了 `#ff9b87`:前者色相算出来是 9.6°,
`QColor::hue()` 取整成 9°,而暗相是 10° —— 被 `lit_keepsTheSameHueAsDark` 判红。
色相 = 60×(G−B)/(R−B),`#ff9b87` 的 R−B=120、G−B=20 → **精确 10°**,与暗相完全相同。
差 1° 肉眼看不出来,但那条测试守的是"色相不许变" —— 与其把判据放宽成"差 1° 算过",
不如把颜色改成精确保色相,反正亮度余量还多要一点(暗相 0.689 → 亮相 0.465)。

### 报警历史库的老库升级路径(2026-10-10)· 纯基建,不含任何 schema 语义

`AlarmRecorder::ensureSchema()` 原本只有 `CREATE TABLE IF NOT EXISTS`。
这个语义的直接后果是:**表已经存在,就什么也不做**。于是老库一旦少了列,
它就一直少着 —— 直到用户现场第一次写报警、或第一次查历史,
SQL 才抛 `no such column: user`。而报警历史是事故追溯的凭据,
那一刻它哑掉,现场是没有任何补救手段的。

新装环境永远建的是完整表,**这条路径压根没人走过** —— 典型"测试全绿、装到现场才炸"。

做法(3 处):

1. **列清单 `kColumns` 成为 schema 唯一真相源**(`AlarmRecorder.cpp` 文件头)。
   `CREATE TABLE` 由它拼出来,老库升级也逐列拿它比对。
   两处共用一份,才不会出现"建表写死 10 列、迁移按 9 列补"这种静默漂移。
2. **`addColumnIfMissing()`**:`PRAGMA table_info` 探测 → 缺才 `ALTER TABLE ADD COLUMN`。
   沿用 `HistoryRecorder::migrateAddHeartbeatColumn()`(D.2)的既有约定。
3. **不引入版本号**,理由见下。

#### ★ 为什么不用 `PRAGMA user_version`

原计划是版本号 bump。查证后否掉了:`AlarmRecorder` 和 `HistoryRecorder`
打开的是**同一个 `history.db` 文件**(`hmi.cpp:531`,`HistoryRecorder::defaultDbPath()`)。
而 `user_version` 是**文件级唯一整数** —— 只要 HistoryRecorder 以后也要记版本,
两个类就互相覆盖对方的整数,谁后 `open()` 谁赢,升级顺序一变就错,
**且不报任何错**。探测式没有这个问题:它问的是"表实际长什么样",
不是"文件自称第几版"。

#### 验证:负向对照(不是只验"加了之后是好的")

新增 4 条用例(`tst_AlarmRecorder.cpp`),每条都从**手搓一个残缺的 D.3 老库**开始
(故意少 `user` / `threshold` 两列),不用 `open()` 建 —— 那建出来的是新表,
正是要模拟的东西的反面。

拆掉迁移循环(留一个临时环境变量开关)重跑,红的是**且仅是**这 3 条:


第二条尤其说明问题:缺列时 `query()` 的 `SELECT ... threshold, user` 直接失败,
返回**0 行** —— 这就是现场"报警历史全空"的样子,不是"报个错"。

`freshDb_isNotTouchedByUpgrade` 在负向对照下**仍然绿**,这是有意的:
新库走 `CREATE` 本来就齐,那条断言只能挡住"清单和实际表结构对不上",

### 改善清单批次 2(续):`TcpClient` 重连"放弃"之后自己复活 · 改善清单 #2

新开 **`tst_TcpClient`**。开这个文件的原因不是"要测新功能",
是 **`TcpClient` 从阶段 1 起就一个测试都没有** ——
它一直在 `HMI_CORE_SOURCES` 里被别的测试间接带着编译,但重连/退避/放弃
这套逻辑**从没被验证过**。改善清单 #2 说的"重入防护不严"就是这么漏下来的。

#### 漏下来的是哪种漏

Qt 连接失败时的信号顺序是**确定的**:`errorOccurred` 先,`disconnected` 紧跟其后。
两个槽都调 `scheduleReconnect()`,平时靠 `reconnectTimer_->isActive()` 挡住第二条。

但"重试到上限放弃"那条分支**故意没有启动定时器** —— 防护失效了。
那条分支又顺手把 `retryCount_` 清成 0,于是紧接着到达的 `disconnected`
看到 `retryCount_ = 0 < maxRetries`,**又排了第 1 次重连**。

后果不是"偶尔多试一次"。是**每一轮放弃后都重启**:
客户端永远停在"重连中",界面上"连接失败"一闪而过 ——
恰好是操作员最该看见的那句话。而**没有任何人按过重连按钮**,是它自己活过来的。

#### 改法,以及它自带的一个更危险的坑

加 `reconnectAbandoned_` 标志,置位后 `scheduleReconnect()` 直接返回。
标志由 `connectTo()`(用户手动重连)和 `onSocketConnected()`(连上了)清掉。

**"放弃"绝不能做成永久状态** —— 那比原 bug 更严重:机器再也连不上。
`tst_TcpClient::abandoned_clearedWhenUserConnectsAgain` 专门盯这一条,
负向对照时它**保持绿**,证明反向没被误伤。

#### 验证:负向对照

去掉守卫重跑,红的是**且仅是**这两条:

```
FAIL!  abandoned_thenDisconnected_doesNotRestartRetryCycle()  abandoned.count(): 2 (期望 1)
FAIL!  abandoned_emitsAbandonedOnlyOnce()                   abandoned.count(): 4 (期望 1)
Totals: 5 passed, 2 failed
```

`abandoned.count()` 是 **2 和 4** 而不是 1 —— 这正是"放弃 → 重启 → 再放弃"的循环,
不是我手写的场景,是我跑出来的。

`errorThenDisconnected_whileTimerRunning_schedulesOnlyOnce` 在负向对照下**仍然绿**,
这是有意的:它验的是"防护本身有效",与"放弃状态要不要粘住"是两件事。

#### ★ 改善清单 #10 复核结论:清单这条是错的,照做会让程序变慢

清单原话"`setSocketOption` 每次都设 → 移到构造",看起来是纯粹的清理。
实测不是 —— 在**未连接**的 `QTcpSocket` 上设 `LowDelayOption` 是 **no-op**,
Qt 直接丢弃这个请求。把 `onSocketConnected` 里那行挪进构造函数后,
连上再读 `socketOption(LowDelayOption)` 拿到的是 **0**:
Nagle 根本没被关掉,每个小 Modbus 帧又慢 ~40ms,**而代码上看不出任何变化**。

维持原样,构造函数处写了长注释防止下一轮再被"优化"回去。

这条测试本身也走了一遍弯路,如实记下来:第一次想直接在 TcpClient 上断言
"连上之后读出来是 0",结果 Actual=1 / Expected=0 **自己先红给我看** ——
因为 `onSocketConnected` 里本来就在设 1,连上之后不管预连接那次有没有生效
读出来都是 1,**分不清是哪一次设的**。分不清来源的断言不算断言。
最后改用两个**与 TcpClient 无关的裸 socket 探针**来隔离这个问题。

验证:`ctest` **67/67 通过**、`hmi.exe` 编译通过(6.67 MB)。

### 悬空指针审计补完 · 一条**我说错了又自己纠正回来**的结论

上一笔把 `PollScheduler` 的 UAF 讲成「用户在界面上删变量」。这次把触发路径查到底,
发现**那句话是错的**,而且已经写进了代码注释 —— 4 处,全部更正:

> 全仓查过:`removeVariable()` **除了测试没有任何生产调用方**,
> `hmi.ui` 里也没有删变量的入口(只有导出按钮和数据显示区)。
> 照着原注释去找触发路径是找不到的。

**真正在生产里踩中的路径更普通** —— 用户点【打开工程】换工程 →
`Project::loadFromFile` 第 4 步 `varMgr_->clear()` 一次删光**全部**变量,
而这发生在**轮询正在跑**的时候。第二遍及以后的换工程必然命中
(第一遍加载时 `start()` 还没跑,容器是空的)。修法不变,可达性理由要换掉。

#### 最后一个没验的持有者:`ThresholdAlarmChecker`

裸 `Variable*`,而它的 `onVariableReplaced` 槽**至今没有任何地方 connect** ——
注释说"由 hmi.cpp 连接",而 hmi.cpp:490 明写那条连接在 E#29 改成"按名查"时被删了。
槽成了孤儿。

**但追到底之后结论是:今天不崩。** `Project.cpp` 第 4 步的顺序是
先 `varMgr_->clear()` 后 `alarmMgr_->clearAll()`,
`clearAll()` 只 `delete`、`~ThresholdAlarmChecker` 是 `= default` ———
`variable_` 悬空的那扇窗口里**没人解引用它**。

这是**碰巧安全,不是设计安全**:代码里没有任何一处表达这个依赖,
而哪天有人往析构或 `clearAll` 里加一行「删之前把变量名打出来」就是 UAF。

#### 我把不变量写错了,测试自己顶了回来(如实记)

第一版测试断言「变量被 delete 的那一刻,`alarmMgr` 里应该已经没有 checker 了」。
实跑 **`Actual=1`** —— checker 那时**确实还活着**,生产里也一样。
我以为的「安全来自两行顺序」是错的,真正的安全来自「窗口里没人解引用」。
把不变量写成那样,是在描述一个不存在的事实。

改成真正可观测的那条:**换工程之后,每条 checker 的 `variable()` 必须正好是
`varMgr_` 里现存的那个指针**(`tst_ProjectSchema::loadFromFile_leavesNoCheckerOnDeadVariable`)。

★ 这条断言有个反直觉的性质,实测出来的:临时加一句拿**已释放指针**做 `QCOMPARE`,
结果不是干净地红,是**直接崩** `0xC0000005`,栈顶
`QTest::Internal::pointerToString<Variable>` —— QCOMPARE 在报告失败时会**解引用**两个指针取名字。
所以断言只能拿确定还活着的指针去比,否则这条测试自己就变成那个崩溃。

验证:`ctest` **67/67 通过**、`hmi.exe` 编译通过(6.67 MB)。

### G-2 崩溃 dump 的【消费端】断了 28 天(2026-10-14 修)

**`crash/pending.txt` 停在 `2026-09-16T09:34:10` / `exception_code=0xC0000005`,
一直没被任何一次启动消费掉。** 现场 92 次成功启动从它身边走过,全程零报错。

#### 根因:写 dump 的和读标记的不是同一个目录

`dumpDirectory()` 原来用 `QStandardPaths::AppLocalDataLocation`,而它是
`AppData/Local/<org>/<app>`,`<org>/<app>` 来自 `setOrganizationName` /
`setApplicationName`。而 `main.cpp` 的启动顺序把元数据排在**后面**:

| 时机 | org/app | 落点 |
|---|---|---|
| `crash::install()`(启动最早期) | ❌ 未设 | `AppData/Local/crash/` |
| **崩溃发生的那一瞬间** | ✅ 早已设好 | `AppData/Local/QianWei/HMI/crash/` ← dump 真在这 |
| `hasPendingDump()`(启动最早期) | ❌ 未设 | `AppData/Local/crash/` ← 从没写进去过 |

`AppData/Local/crash/` 这个空壳目录 **2026-09-08 16:28:38 就建好了** ——
正好是本项目第一次运行的时间,也就是这个顺序 bug 从第一天起就一直在。
它至今为空。

**叠加的第二个问题**:`main.cpp` 原本在 `QApplication` 构造**之前**就
`QMessageBox box; ... box.exec();`。`QMessageBox` 是 `QWidget`,
没有 `QApplication` 实例就构造会直接 abort ——
也就是说**就算路径对了,弹框自己也会把进程打死**。

#### 为什么 28 天没人发现

`CrashHandler.cpp` **此前零测试覆盖**:它根本不在 `hmi/tests/CMakeLists.txt`
的 `HMI_CORE_SOURCES` 里,69 个测试文件里没有任何一个碰过它。
「写 dump」和「崩了有人知道」是两件事,后者一直没被测过。

#### 修法:把路径变成纯函数,而不是靠注释约束调用顺序

```cpp
const QString base = QStandardPaths::writableLocation(GenericDataLocation);
return base + "/QianWei/HMI/crash";     // 常量,不读全局状态
```

**为什么不只是把 `main.cpp` 的语句顺序调对**:顺序是被注释约束的,
纯函数是被测试守着的。只要"调用方什么时候设了什么"还会漂移,
漂移的后果就是崩了却没留下任何可分析的现场 —— 而那是唯一能救命的时刻。

org/app 收成 `crash::kOrgName` / `kAppName` 两个常量,`main.cpp` 也从那儿取,
杜绝两边各写各的。`main.cpp` 两处顺序调整(元数据提前、弹框挪到
`QApplication` + SingleInstance 之后)仍有价值:后者顺带防止**第二实例
把主实例该报的崩溃信息吃掉**。

新增 `HMI_CRASH_DIR` 环境变量可覆盖 dump 目录 —— 运维用来把客户现场的
dump 收到已知路径,测试用来隔离。

#### 我在这次修复中弄坏的东西(如实记录)

新写的 `tst_CrashHandler.cpp` 最初在 `cleanupTestCase` 里写了
`QDir(crash::dumpDirectory()).removeRecursively()`。

`initTestCase` 失败就跳过 `cleanupTestCase` —— 于是那句递归删除

教训:**护栏只保护它自己所在的函数,不够。** 测试不配拥有"递归删除任意路径"

### G-3c 补测试逮到一个【假 setter】:`setTimeoutMs` 改了字段、没改计时器(2026-10-14)

做 `--soak` 时要改 `InactivityWatcher` 的**生命周期**(soak 时跳过
`installTo` / `start`),顺手给它补测试 —— 因为它此前**零覆盖**。

> 这跟【改善清单 #13】撞的是同一面墙:**【没有测试 ≠ 改动安全】**。
> 只不过这次撞上的是一个**安全特性**,而它刚被改了启动时机。

#### 根因:一个安静的假 setter

```cpp
// 修复前
void setTimeoutMs(int ms) { timeoutMs_ = ms; if (timer_->isActive()) start(); }
```

它只改**成员变量** `timeoutMs_`,**从没调过 `timer_->setInterval()`**。
而 `setInterval(timeoutMs_)` 只在**构造函数**里调过一次(`InactivityWatcher.cpp:19`),
之后 interval 再没被同步过。那个 `if (timer_->isActive()) start()` 也只是
**重新启动**计时器,启动时用的是 timer 上**现存的 interval** —— 还是 5 分钟。

**危害**:不崩、不报错、**安静地不生效**。调用者以为"超时改成 30 秒了",实际 5 分钟。
代码读起来完全合理,行为却不跟字面意思走 —— 这类 bug 最难查。

#### 负向对照:回滚修复后重跑(7 passed / 5 failed)

回滚成修复前那一行式版本,`tst_InactivityWatcher` 精确变红,
且**红的正是修复前那同一批 5 条**:

```
Totals: 7 passed, 5 failed, 0 skipped
```

日志顺手把铁证打出来了 —— **字段和计时器对不上**:

| 用例 | `installTo` 日志里的 `timeoutMs` | 计时器实际走的 | 结果 |
|---|---|---|---|
| `setTimeoutMs_actuallyChangesTheTimer` | `300000 ms` | 300000 | 红 |
| `installTo_thenStart_armsTimer` | **`50 ms`** | 300000 | 红 |

第二行是最有说服力的一条:字段已经是 50 ms,日志也**照实打了 50**,
**信号就是不来**。两处数字对不上,就是"假 setter"的全部含义。

恢复修复后 11/11 全绿,`git diff` 行数回到 23/2,与回滚前逐字一致。

### G-4 `build.ps1` / `build_tests.ps1` 的编码陷阱(2026-10-14)

两个脚本各有 104 / 116 个汉字却**都没有 UTF-8 BOM**。PowerShell 5.1 对无 BOM
的 `.ps1` 按系统 ANSI 代码页(本机 936/GBK)解码,而 **GBK 解码 UTF-8 字节时

### 阶段 I:安装包(2026-10-14 链路打通,**仍未产出 .exe**)

**做了什么**:新增 `installer/package.ps1`,把三步绑死成一条命令:

```
powershell -ExecutionPolicy Bypass -File .\installer\package.ps1
```

1. Release 构建(`--preset Qt-Release`)→ `out\build\release\hmi.exe`
2. `windeployqt --release --no-translations` → `installer\install_root\`
3. `ISCC.exe installer\hmi.iss` → `installer\Output\hmi-setup-0.2.0.exe`

**为什么要有这个脚本**:打包链三步,每一步忘了前面那步都会得到一个
**【看起来成功、实际不能用】**的包。第 2 步(windeployqt)最阴险 ——
在本机跑得好好的(自己机器装了 Qt),拷到别人机器上就死。

**实测(2026-10-14)**:

- ✅ 第 1 步绿:Release 构建通过
- ✅ 第 2 步绿:收齐 **40 个文件 / 88.6 MB**(hmi.exe + 8 个 Qt6 DLL +
  platforms/styles/sqldrivers/imageformats/tls 等 9 个插件目录)
- 🔴 **第 3 步没跑**:本机**没装 Inno Setup**(`ISCC.exe` 两个常见路径都没有)。
  → **目前仍然没有一个能发给用户的 .exe。** 装完 Inno Setup 6 重跑脚本即可。

**已验证到哪一步**(不能含糊):`install_root\hmi.exe` 在**把 Qt 从 PATH 里摘掉**的
情况下启动,退出码 0 —— 即 DLL 依赖能就地解析,这是"拷到别人机器上起不来"那个故障的
直接反证。⚠️ 但这一条**不能证明安装包可用**:`SingleInstance` 的守卫在
`QApplication` 构造**之前**就返回了,程序根本没走到加载插件那一步。

**两处被负向对照逼出来的坑(改错了也看不出来的那种)**:

1. **`windeployqt` 不复制 `hmi.exe` 本身**。它只收依赖,exe 要自己拷。
   而 `[Files]` 是整个 `install_root\*` 收进去 —— 不拷就是**打出一个一个程序都没有
   的安装包**,而且安装过程一切正常。现在脚本里有显式 `Copy-Item` + 断言。
2. **`-SkipDeploy` 不能跳过断言**。跳过 windeployqt 时若上次的 `install_root`
   不完整,同样会打出空包。断言已提到 `-SkipDeploy` 判断之外。

**顺带修掉的**:`hmi.iss` 的 `[Files]` 原是占位的 `Source: "x64\Release\hmi.exe"`
—— 那个路径**根本不存在**。就算装了 Inno Setup,编出来也只有一个裸 exe。
