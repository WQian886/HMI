## 三、分层架构(7 层 + v0.2.0 新增子层)

```
UI(hmi)              ┐  3 个状态机 State/ConnState/ModbusState,唯一出口 updateUi()
业务协调(AlarmManager / ActionManager) │
业务执行(ThresholdAlarmChecker / WriteFailChecker) ├─ Qt signal/slot 是唯一调度机制
调度(PollScheduler / WriteScheduler) │  100ms tick,唯一的"主动推"
协议(IPollDriver 抽象 → ModbusDriver / S7Driver / EipDriver) │  v0.2.0 C 阶段抽象层
传输(TcpClient)      │  连接/指数退避重连/心跳
数据(Variable / VariableManager) │  tag/value/quality/deadband/range/dirty
配置(Project / JsonSerializer) ┘  JSON 存读

=== v0.2.0 新增的旁路子系统(走信号槽,不影响 7 层主轴) ===
A 阶段:logging/  crash/  instance/  tray/
B 阶段:auth/(UserStore / UserManager / PasswordHasher / AuditLog / LoginDialog / ...)
D 阶段:history/(SQLite) / export/(CsvExporter) / tag/(ExpressionParser / TagImporter)
E 阶段:widgets/(22 控件) + editor/(PaletteWidget / EditorMainWindow / PropertySheet / GeometryChangeCommand / ControlListCommand / RuntimeCanvas / ...)
```

**关键事实**:全部 7 层都在**主线程**,没有 QThread / QtConcurrent,emit/slot 同步触发。
唯一的主动驱动是 Poll/WriteScheduler 的 100ms tick + 历史库 60s 心跳 tick,其余都是被动响应。

详细的 5 条流程(启动/读/写/报警/存读)见 `docs/专题/2026-08-09_调度机制.md`。
E 阶段编辑器架构见 `src/editor/EditorMainWindow.h`。

## 四、两条数据流(项目灵魂)

**读(PLC → UI)**
`PollScheduler::onTick`(100ms)→ 挑到期变量 + 合并连续地址 → `ModbusMaster` 组帧 →
`TcpClient` 发出 → 响应回来拆帧 → `Variable::setValue` → `emit valueChanged` →
`Binding` 刷新 QLabel。**并行通道**:`emit rawRead` → 报警检查(绕开死区过滤)。

**写(UI → PLC)**
用户在 QLineEdit 回车 → `Binding::bindEdit` 校验 → `setValue` + `markDirty` →
`WriteScheduler::onTick` 扫 dirty → 发 Modbus 写 → `writeFinished` → `clearDirty` + 审计日志。
失败保留 dirty 下帧重试,超过 `kMaxWriteRetries`(3)→ `emit writeFailed` → 报警。

## 五、写代码必守约定

1. **事实 → UI 单向流**:业务只改 `state_ / connState_ / modbusState_` 等"事实",再调 `updateUi()`。
   **绝不在槽函数里直接 `setText`。**
2. **信号转发链分层**:`QTcpSocket → TcpClient → hmi`,上层不认识底层 socket。
3. **加新 `.cpp/.h` 第一步必须同步 `hmi.vcxproj` + `hmi.vcxproj.filters`**
   (带 `Q_OBJECT` 的要进 QtMoc),否则 LNK2019。
4. 超时/重试/周期等用 `kXxxMs` 常量,不散落 magic number。
5. **持有裸 `Variable*` 的模块必须 connect `VariableManager::variableReplaced`**,
   否则 loadFromFile 后是悬空指针。原因见 `docs/专题/2026-08-27_ActionManager报警联动与悬空指针.md`。
6. 注释格式:`★ IMPROVE-x.y(日期)` + `【背景】【改法】【取舍】【参照】`。
7. 改动源码需 Wqian 同意;改工作区文件需当条消息显式授权。

### ⚠ VS 2026 的 ucrt 坑(必读,别再踩)

VS 2026 v18 的 `vcvars64.bat` 只把 `um/shared/winrt/cppwinrt` 加进 INCLUDE,
**漏了 `ucrt`** → 报 `error C1083: 无法打开包括文件: "stddef.h"`。

**两条无效解**(别浪费时间):
- `set INCLUDE=...;%INCLUDE%` —— MSBuild 会重置 env,不生效
- `/p:IncludePath="ucrt;$(IncludePath)"` —— 编译过但 link 找不到 `kernel32.lib`
  (此时 `$(LibraryPath)` 还没被 props 赋值,被整体替换成只剩 UCRT)

**真稳修法** —— 改 `hmi.vcxproj.user`(VS 标准用户级覆盖,不污染 vcxproj / git):

```xml
<PropertyGroup>
  <IncludePath>$(IncludePath);C:\Program Files (x86)\Windows Kits\10\Include\10.0.26100.0\ucrt</IncludePath>
  <LibraryPath>$(LibraryPath);C:\Program Files (x86)\Windows Kits\10\Lib\10.0.26100.0\ucrt\x64</LibraryPath>
</PropertyGroup>
```

这两个属性在 props sheet 设置**之后**追加,VS IDE 和命令行都生效。

**命令行构建**(工程根):
```cmd
"D:\Program Files\Microsoft Visual Studio\18\Community\VC\Auxiliary\Build\vcvars64.bat"
"D:\Program Files\Microsoft Visual Studio\18\Community\MSBuild\Current\Bin\MSBuild.exe" hmi.slnx /t:Build /p:Configuration=Debug /p:Platform=x64 /m
```

#### F1:报警历史存出孤儿行(已修)

`AlarmManager::onCheckerRecovered` 的顺序是 **erase → emit**:

```cpp
it->recoveredAt = now();
activeAlarms_.erase(it);        // ← 记录没了
emit alarmRecovered(id);        // ← 只传 id
```

而 `AlarmRecorder::onAlarmRecovered` 靠**遍历 `activeAlarms()`** 取完整数据 ——
刚 erase 的那条**必然遍历不到**,直接走兜底 `insertAction(id, {}, 0, ...)`。

**结果:历史表里每一条"恢复"行的 `name`/`level`/`variable_name`/`trigger_value`/`threshold` 全空。**
事故追溯查出来是一行只有 id 和时间的孤儿。

**为什么两个月没人发现:** 旧测试 `recordRecovered_writesActionTwo` 只断言
`action==2 && id 匹配` —— 恰好是这条路径上**唯一没坏的两样**。
断言挑在了不会红的地方。

**修法**(不只是调顺序):

1. 恢复的记录进 `archived_`(有界 500 条)而非直接销毁 —— 只调顺序的话
   `acknowledgedAt`/`state` 照样当场蒸发,「没来得及确认值就回来了」这种
   现场最常见的情况无从回答
2. 信号多带一个 `const Alarm&` —— 下游不必回查一个可能已空的容器
3. `state` 置 `Cleared` —— 这个枚举值定义在 `Alarm.h:24` 一直没人写,是死代码
4. `clearAll()` 连存档一起清 —— 换工程时 `findAlarm()` 会串到上个工程的数据

**改信号签名的回归风险已钉住**:全仓有两个消费者是老签名(只接 `qint64`)——
`hmi::onAlarmRecovered`(`hmi.cpp:1350`)和
`AlarmListControl::onAlarmRecovered`(`AlarmListControl.h:49`)。
Qt 允许"多参信号 → 少参槽"所以不影响它们,但**没有编译期检查兜底**:
失配的症状是"UI 不更新了",跟代码看着没问题完全不搭边。
`legacyIdOnlySlot_stillReceivesRecovery` 专门钉这条。

**测试有效性已反向验证**:临时把行为改回旧的 erase 顺序,

#### 我自己的一处误判(已纠正,别再犯)

开工时判断:`active_` 一个 bool 同时表示「待触发」和「已触发」,
所以报警恢复后再超限会**重报同一条报警** —— 记成了 bug,立了任务 #14。

**拿修复前的代码跑,那条断言是绿的。** 它描述的是原有行为,不是缺陷。

真实结论:**高 → 正常 → 再高报两次是正确的工业语义** —— 两次就是两次独立工况,
操作员需要知道"它又犯了一次"。压错了报警,比多报一条危险得多。

该压掉的只有 **chatter**:模拟量在阈值附近来回摆,且**每次越线都超过
`minDurationMs`**(所以防抖挡不住),形成一串完整的 触发→恢复→触发。
用例把这点钉住了:无滞回时 4 轮摆动 = **4 次触发 + 4 次恢复**。

#### 改了什么

- `CheckerConfig` 加 `hysteresis`(默认 `0.0` = 不启用),`JsonSerializer` 读写
  `hysteresis` 键。老工程没这个键 → 回落 0,**行为与 5.3 逐位相同**。
- 状态机 `bool active_` → 显式三态 `Idle / Pending / Fired`。
  滞回**只在 `Fired` 档生效**:已报警后须跌到 `threshold ∓ hysteresis` 才算恢复。
  这是保留三态的真正理由 —— 单 bool 区分不了「待触发」和「已触发」,
  滞回没地方挂。**但这是为滞回铺路的重构,不是 bug 修复**,两者别混为一谈。

#### 反向验证(不是"改完看着对了")

| 用例 | 修复前 | 修复后 |
|---|---|---|
| `chatter_slowOscillation_isSuppressedByHysteresis` | **红**(4 次触发 / 期望 1) | 绿 |
| `hysteresis_valueInDeadBand_doesNotRecover` | **红**(死区内就报了恢复) | 绿 |
| 其余 6 条 | 绿 | 绿 |

> 照样每次都报。用例第一版把低点写成 30,测试红着才发现。

### F2-c 报警屏蔽(shelve)✅ 2026-09-30 完成

滞回压的是"报太多";屏蔽解决另一类:**"这条报警现在没意义,别烦我"** ——
传感器检修中、某台泵本来不投用,它的报警纯属噪声。

**放在 `AlarmManager` 而不是 Checker**,三个理由:

1. `onCheckerTriggered` 是所有 checker 报警的**唯一收口点** → 阈值报警、
   写失败报警等**所有类别**一致受管(放 Checker 里就只有阈值报警能被屏蔽);
2. 状态可查 / 可撤销 / 可枚举(界面据此显示"N 条被屏蔽");
3. `clearAll()` 一次清干净,换工程不会带着上个工程的静默名单开局。

**静默屏蔽比不屏蔽更危险 —— 这是本功能的硬约束**

若"被屏蔽的 checker 不触发"是唯一表现,屏幕上就没有行、没有计数、没有日志,
操作员会以为"这次真没报警",实际是**被我们藏起来了**。更糟的是检修结束忘了
取消屏蔽 → 传感器真的坏了 → 依然没有报警。**设备坏了而界面一片安静,这是能出人命的。**
所以三条硬约束:`shelveCount()` 随时可查 / `shelveChanged` 让界面自己跳出来 /
屏蔽必须能撤销(不是单向门)。

**屏蔽的是"进不进系统",不是"检测器还测不测"**

拦截在 Manager 层,`ThresholdAlarmChecker` 照常在算、传感器照常在越线。
调试时看到"检测器还在报但界面没反应"是正常的;反过来若连检测一起停,
故障就彻底不可见了 —— 那比多报一条危险得多。

**没做:自动到期。** 工业上常见"屏蔽 8 小时自动恢复",本次不做 ——
需要常驻定时器 + 到期语义 + 跨重启策略,而项目连报警编辑 UI 都还没有(配置只能手改 JSON)。
宁可只落"手动可撤销"这一半,也不做出一个"以为会自己恢复、实际不会"的半成品。

#### 反向验证

### F4 报警历史查询(2026-10-08)· 存了三个月的历史,终于看得见

D.3 把报警落库做完了,主窗口的"报警历史"tab 却一直是个占位 Label ——
**存了但看不见的历史等于没有历史**。出了事故要复盘,连"昨晚到底报了什么"都答不上来。

现在能按**时间范围**(手选 + 1 小时/24 小时/3 天/7 天快捷)和**等级**查了,
**最新的排在最上面**,0 条时明确说"该条件下没有记录"而不是留一张空表。

**三件写下来才想明白的事:**

**1) 那一栏必须写"最低等级: 严重及以上",不能写"等级 = 严重"。**
`AlarmRecorder::query` 的第三个参数是 `minLevel`,它是**下限**不是集合,
选"严重及以上"会把危急一起带出来。界面上写"等级 = 严重"的话,
用户看到危急的记录不见了,会去查"危急报警是不是没记录" —— 而它好好地在库里。
**这是界面在撒谎,比缺功能更糟。**

**2) 最新的排在最上面,但改的是视图不是 query。**
`AlarmRecorder::query` 是 `ORDER BY action_at ASC`,那是**导出 CSV** 要的顺序
(事故分析从头顺着读下来最顺)。但操作员点开"报警历史"是想看"刚才发生了什么",
让他自己翻到最后一行去找,等于没有这个界面。
两种顺序各有各的用处,改全局会连 CSV 导出和现有测试一起改掉,
所以 `std::reverse` 放在表现层 —— 同一份数据,**给人看的倒着排,给机器读的顺着排**。

**3) 等级和动作两列全是乱码,一条用例绊出来的。**
报错打印 Actual 是 `ä¸¥` —— 肉眼看过去**就是"严重"两个字的乱码形状**,
很容易以为是自己期望值写错了。真病根在实现:显示用的字面量是源码里的 UTF-8,
代码却用 `fromLatin1` 转,"严"的 3 个字节 `E4 B8 A5` 被当成 3 个 Latin-1 字符。
名字那一列一直是对的(直接从库里取的 QString),
**正是这种"别的列好好的、就这两列是乱码",最容易让人以为是数据问题。**

**区域过滤没做,卡在 Wqian 的设计决定上。**
整个代码库里**没有"区域"这个概念** —— `Alarm` 结构里没这个字段,工程文件里也没有。
要支持就得先给报警加字段、动 schema,那是会改工程文件格式的决定,不是界面层能顺手加的。
三个选项写在 `AlarmHistoryView.h` 里:a) 给 Alarm + 工程文件加 `area` 字段(有迁移问题)
b) 暂时只按时间/等级,真有需求再说 c) 拿画面当区域复用(但报警和画面目前没有关联)。
**在拍板之前界面上不出现"区域"字眼**,免得用户去找一个还不存在的功能。

### F5 报警声音 / 蜂鸣(2026-10-08)

选 Windows `MessageBeep` 而不是 Qt6::Multimedia —— 不用为一声蜂鸣再装一个 Qt 模块。
`setSoundSink()` 是留给将来的替换口。

4 档等级分别用不同系统提示音(信息默认不响)/ **确认即静音** /
**重复提醒直到确认**(默认 5 秒一圈,每圈只响一次、按当前最高等级响)/
**静默时段**(默认 22:00–7:00)/ 主窗口"报警声音"按钮 + 带试听的设置对话框。

**决策逻辑 `decide()` 是纯函数,完全可单测;声音有没有真的出来测不了**
(没有 CI 声卡,`MessageBeep` 也不返回任何东西)。`tst_AlarmSound` 27 条测的是决策。
**绿灯之后仍然必须人耳验一次。**

**写这一节挖出两个真 bug:**

- **静默时段里触发的报警,过了静默时段就再也不响了。**
  重复提醒定时器在静默时段被停掉,而**没有任何东西会再把它启动起来** ——
  于是凌晨 2 点触发的一个危急报警,一直安静到它自己恢复为止。
  修法:`onRepeatTick()` **必须按"还有没有待处理的报警"来停,不能按"这一圈有没有响"。**
  静默时段里 `decide()` 全返回 `SilencedByQuietHours`,按后者判断定时器会 22:00 就停掉。
- **`pendingReminderCount()` 一开始错算了静默时段。**
  我最初让"待处理" = "这一圈会响",那么晚上界面会显示"0 条报警",
  而一个没人处理的危急报警就躺在活动列表里。已纠正:这个计数**刻意不考虑静默时段**,
  和 F2-c 的"**静音不能等于隐藏**"是同一条原则。

### F3-b 运行时画布的报警列表会闪了(2026-10-08)· 但也踩中了一个"我自己写的注释是假的"

补的是第七节那条 🟡 的前半截:运行时画布上的 `AlarmListControl` 原来**根本不闪**,
而 E.5 之后操作员实际盯的是运行时画布 —— 也就是"会闪的那套"不在他眼前。

- **速度对齐 500ms**,取主画面 `hmi.cpp:423` 的同一个值。两套 UI 各闪各的、
  速度还不一样,操作员目光在两者间来回会觉得"这边快了一点"。
- **判据对齐** `hmi.cpp:1492`:未确认 + 严重/危急。
  信息/警告闪 = 现场最吵的永远在闪,真出事的那条被淹了;
  已确认的还闪 = 骗操作员去处理一条已经处理过的。
- **定时器必须会停**:有该闪的行才开表,一个都没有就停,而且停之前把相位复位。
  这是 7×24 的工控机,没报警时让事件循环一直醒着是纯浪费。
- **相位复位是有理由的**:不复位的话,下一轮启动的第一帧是暗相,
  而那一行的颜色可能还停在亮相的深色上 —— 用户看到"新报警颜色不对,过一会儿才对"。

#### ★ 关键设计:闪的是【亮度】,不是【换一套颜色】

主画面 `hmi.cpp` 闪的时候直接换成 `QColor(255,80,80)` / `QColor(255,200,100)`。
**F3-b 没跟**:那样写的话危急/严重/警告会共用一个红 ——
而"哪一档"正是颜色在表达的信息,操作员靠它分轻重,闪一下就分不出来了,闪烁反而害事。

于是定为:**闪烁 = 本档底色变亮/变暗,色相不变**。
闪 = 在说"这条还没处理";颜色深浅 = 在说"这条有多重"。两件事各走各的通道。
所有改颜色的地方仍然只有 `repaintRow()` 一个(闪烁也走它),
两处各配一次色必然出现"闪一下之后颜色停在错误档位"这类 bug。

#### ★ 这里我写了一句假注释,然后用 WCAG 算出来打自己的脸

`repaintRow()` 里最初写的是亮红 `#f05a5a` 配白字,注释还特意标了
"保证对比度不降"。**那句话是假的。** 拿 WCAG 相对亮度公式算:

| | 底色 | 字色 | 对比度 |
|---|---|---|---|
| 危急 暗相(原来) | `#cd2828` | 白 | **5.34:1** |
| 危急 亮相(原写法) | `#f05a5a` | 白 | **3.33:1** ← 掉了一截 |
| 危急 亮相(改成) | `#f05a5a` | `#3b0606` | **5.20:1** |
| 严重 暗相 | `#ffcdc3` | `#780a05` | 6.15:1 |
| 严重 亮相 | `#ff9682` | `#780a05` | 5.39:1 |

即:**闪烁最亮的那半拍,恰恰是字最难读的那半拍** —— 而那正是操作员
最想看清"哪条报警、多严重"的时候。根因是底色一提亮白字必然失效,
两者不能同时要;解法是**亮底配深字**,亮度还能比暗相亮 81%(余光绝对抓得到)。

**这条必须变成测试,不能只留注释。** 注释是写给我自己看的,下一次调色的人未必会重算;
而"字看得清"和"底色够亮"在屏幕上长得完全不一样,没人会拿两个色块数字去比。
→ `tst_AlarmListControl::blink_textStaysReadableInBothPhases`,阈值 4.5:1
(WCAG AA 对正文的最低要求)。已用变异验证:把字色改回白字,该用例立刻红,
并报出 `Emergency 亮相对比度只有 3.33:1`。

**代价要说清楚**:危急在亮相那半拍不是白字了(`styleFor` 里"唯一用白字的档"只对静止态成立)。
取舍理由是"看得清"优先于"用白字标识最重的那一档" —— 后者只是个约定,前者是能不能读。

#### 测试写法:为什么不睡 500ms

5 条新用例全部用 `advanceBlinkForTest()` 手动走相位,**没有一条 `QTest::qWait(500)`**。
"睡 500ms 再看一眼颜色"既慢又不稳:CI 上一旦机器忙,500ms 里定时器可能没被派发,
断言就会随机红 —— 而红的原因和被测逻辑毫无关系。

两条变异都实测过(改前是绿的):

| 变异 | 结果 |
|---|---|
| 亮相不上色(`blinkOn_ && false`) | 2 条红:`dark != lit` / `critLit != critDark` |
| 亮红配白字(最初那版) | 1 条红,报出 3.33:1 这个具体数字 |

#### 这条没解决什么

**闪烁实现仍然是两份代码。** 主画面 `hmi.cpp` 那套原封不动,配色也和 F3-b 不同
(那边是"换成醒目红/橙",这边是"本档变亮")。真要统一得先定"报警闪烁的配色权威在哪一处",
那是改产品行为,是 Wqian 的决定 —— 所以第七节那条只标了"已补运行时画布",没划掉。

#### 二、待办里"EXCLUDE_DIRS 应跳过 `3rdparty/`"这条**照做会编译失败**
