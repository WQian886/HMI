## 1. 静默失败:键名对不上,代码会【假装成功】

**现象**:`tst_LabelControl` 等 10 个测试文件的 `fromJson` 用例长期红。失败信息只说
"期望 100,实际 0",完全看不出哪里错了。一直被当成"基线失败"记着,谁也没深究。

**根因**:`ControlBase.h:43-44` 的 Q_PROPERTY 是 `position` / `size` / `variableName`。
`propertiesFromJson` 按 **Q_PROPERTY 名**反查,`obj.contains(name)` 不中就**跳过**。
而测试写的是平铺的 `x` / `y` / `w` / `h` / `variable` —— 一个都匹配不上,
**整个对象被静默忽略**,控件保持默认值。跳过不是报错,是因为"缺字段用默认值"
本来就是 `fromJson` 想要的容错行为(工程文件版本兼容要用)。

**归因更正**:此前文档把这条记成"生产代码 `toJson`/`fromJson` 键名不匹配(w/h vs width/height)"。
**那是错的。**生产代码 `toJson`/`fromJson` 是**对称**的(反射输出 `position`/`size` 嵌套对象,
反射读回来),一个字都不用改。错的是**测试在断言一个从未存在过的 JSON 格式**。

**教训**:

1. **静默失败比崩溃难查一个数量级。** 崩溃会告诉你哪行错了;"跳过 + 用默认值"什么都不说。
   写容错分支时问自己:**这个 `skip` 分支能不能也留个 `qWarning()`?** 现场改不动代码时
   至少能留个线索。
2. **失败信息读不出来,就去看输入,别看实现。**"值不等"看不出键名问题;
   把测试构造的 JSON 打印出来跟 `toJson` 的实际输出比一眼就知道。
3. ★ **"只验 `toJson` 输出"的测试,两边一起错也照样绿。**
   `tst_LabelControl` 原来就是这种:它断言 `toJson()` 输出的字段名,
   字段名跟 `fromJson` 期待的字段名**同时错**的话,测试是绿的,功能是坏的。
   **每个序列化测试都必须成对写 `toJson → fromJson → 比对原值`**,单独验任何一头都留一半盲区。
   (这次补的 `toJson_fromJson_roundTrips` 就是干这个的。)

**怎么避免**:新写序列化测试时,先跑一次 `toJson` 把输出打出来照着写 `fromJson` 的输入。
不要凭"我记得字段叫什么"写。

## 2. 工厂注册靠构造函数 → 新控件漏一行 = 两个静默症状

**现象**:`tst_MotorControl::pumpAndMotor_areDistinctTypes` 报「Pump 不在注册表里」。
Pump 明明写好了,头文件也 include 了。

**根因**:`ControlBase.cpp` 里的工厂 `QHash<QString, FactoryFn>` **由每个控件的构造函数**
调 `registerControlType` 填充 —— 不是静态初始化。`EditorMainWindow.cpp` 开头有一串

```cpp
delete new LabelControl; delete new NumberDisplay; ...
```

就是**为了逼所有控件的构造函数跑一遍把注册表填满**(所以是 `delete` 不是正常用)。

**后果**:新增的 5 个控件没被加进那串 `delete` →
① 调色板上**不出现**这 5 个控件
② 工程文件里**存着它们**,但 `loadFromFile` 静默跳过

**教训**:

1. 两个症状都是「看起来坏了但说不清哪坏」—— 调色板少 5 项、工程文件里有但画布上没有。
   静默失败再一次。
2. **加控件的 checklist 必须包含"往 `EditorMainWindow.cpp` 的 delete 串里加一行"**,
   而且要**写在代码注释里**(已在 `EditorMainWindow.cpp` 加了带警告的注释块),
   因为漏了不会有任何编译错误。
3. **判断漏没漏的最快办法是数数**:调色板项数 < 22 就是漏了。已有断言
   (`tst_EditorMainWindow::palette_listsAllRegisteredControls` 硬编码 `QCOMPARE(count, 22)`)。

**附带教训**:单测文件之间**不共享注册表状态**。`tst_MotorControl` 里要断言 Pump 已注册,
得先 `delete new PumpControl;` 触发一次注册 —— 静态初始化顺序问题在测试里同样会咬人。

## 3. `QAbstractAnimation::currentLoop()` 是 public;自己数圈数会丢整圈

**现象**:`SpinAnimator`(泵/电机共用的转子动画)原代码:

```cpp
const qreal delta = next - static_cast<qreal>(lastLoop_ * 360);
if (delta < 0.0) ++lastLoop_;     // ← 永远不会成立
angle_ += delta;
```

**问题**:`next` 恒 ≥ 0(动画 0→360),所以 `delta` 恒 ≥ 0,**`lastLoop_` 从不递增 —— 整段是死代码**。
更要命的是纯累加:一旦卡一帧(角度从 355 直接跳到下一圈的 5),累加以为只走了 5°,
**丢掉整整一圈**,表现为泵的转速随卡顿忽快忽慢。

**修法**:`angle_ = offset_ + anim_->currentLoop() * 360 + v.toReal();`
`currentLoop()` 是动画自己维护的真实圈数,跟帧率无关。新增 `offset_` 让
**停止后重启从停下处续转**而不是跳回 0°。

**教训**:

1. ★ **`QAbstractAnimation::currentLoop()` 是 public,`currentLoopChange()` 是 signal。**
   我第一版修复的注释里把后者写成"protected 所以不能用" —— **写错了,读文档摘要没验证就下结论**。
   这是本项目第三次犯"照着文档摘要改代码没跑测试"的错(前两次是 QColor 的两次误判)。
   **写完注释里对 API 可见性的断言,顺手用一次编译器验。**
2. **凡是 `if (条件) 计数器++;` 这种看着就有点怪的地方,先问"这个条件成立过吗"** ——
   死代码不会报错,只会让后面所有基于它的推理都建立在空气上。
3. 单测里手动喂帧(`applyFrame(value, loop)`)比跑事件循环靠谱:
   掉帧这种时序 bug 靠 `QTest::qWait` 复现要碰运气。

**另一个设计点**:把算式抽成独立函数 `applyFrame(value, loop)` 给测试用,
而不是让测试**重算一遍公式**。重算 = 把公式抄成两份,以后改了生产代码测试还在测旧公式,
而且**永远是绿的**。

## 4. 顺手记一条(不算 bug,但同源)

**`setPos()` 和 `setPosition()` 是两条路径。**`setPos` 走 `QGraphicsItem::itemChange`,
`setPosition` 走自己的 setter → emit `positionChanged`。E.4d-follow-6 只在 `itemChange` 里
补了 `positionChanged`,结果用 `setPosition` 改位置的路径属性面板不刷新。
**加信号时要把所有公开的写入口列一遍**,别只盯 Qt 自己的那个。

## 5. `NOTIFY` 里的信号可能不住在声明该属性的类上(`error C2039`)

写旋转那块的连接时顺手写了个:

```cpp
connect(t, &QGraphicsItem::rotationChanged, this, ...);   // ❌ C2039
```

`QGraphicsItem` 的 `Q_PROPERTY(qreal rotation READ rotation WRITE setRotation
NOTIFY rotationChanged)` 明明写在头文件里看着就能用,但那个 `void rotationChanged();`
实际声明在 **`QGraphicsObject`** 里(`qgraphicsitem.h:530`,`QGraphicsItem` 从 46 行开始,
`QGraphicsObject` 从 485 行开始)。

**信号要有 moc 才存在,得有 QObject 基类。**`QGraphicsItem` 不是 QObject,所以那条信号不在它身上。

正确写法是**经派生类取**:`connect(t, &ControlBase::rotationChanged, ...)` —— `ControlBase`
继承自 `QGraphicsObject`,moc 认。

> 读头文件找声明位置时,**别看 Q_PROPERTY 那行在哪** —— 那行只是元数据,连的是信号。
> 要顺着信号名一路找到 `void xxx();` 实际落在哪个 class 里。
> 今天的另一个教训(`currentLoop`)也是同一类:**文档摘要 ≠ 代码**。

## 6. 计划书写得越细,越容易不去验证

今天收口的两条尾巴,计划书都附了详细的改动清单和风险等级。**回头对账,5 条建议里 3 条是多余的**:

- 「给 `ControlBase` 加 `Q_PROPERTY(qreal rotation)`」→ `QGraphicsItem` 自己就有,不是 FINAL,反射已经能用。
  照做会变成子类覆盖父类同名属性 —— moc 允许,但凭空多一层间接,**底下那层还在跑**。
- 「让 8 个 handle 位置跟着转」→ handle 是 target 的**子 item**,Qt 的父子 transform 已经在做了。
  加一套旋转换算会跟 Qt 重复,还多一个能算错的地方。
- 「补 `paint()` 的蓝色虚线」→ 笔刷构造时就配好了,渲到 QImage 一数就有。

真正坏掉的只有 **handle 光标** 和 **选中框** 两处,加起来不到 100 行。

**根因不是判断力差,是没先读代码。**三处里两处的正确答案,读一眼头文件/父类关系就有,
但计划书一旦把"风险等级""改哪几处"列成表格,读起来就像已经调查过了。
