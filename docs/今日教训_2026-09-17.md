## 1. 架构/设计教训(6 条)

### 1.1 接口设计要预留扩展空间(C.1)

**坑**:原 PollScheduler 用 `QModbusDataUnit` 太具体,加 S7 必须改 PollScheduler。

**教训**:第一次设计接口时,问"未来加协议时这个接口要改吗?" → 如果要改,再抽象一层。

**怎么避免**:C.1 抽 `IPollDriver` + `RegisterArea enum`(4 种)+ `QVector<quint16>` 而非 `QModbusDataUnit`,S7/EIP 直接复用。

### 1.2 100% 行为兼容是迁移的硬指标(C.1)

**坑**:把 `ModbusMaster` 包成 `ModbusDriver` 时,如果改任何行为,所有现有测试会破。

**教训**:扩展/重构前,先把"零行为变化"列成验收标准。

**怎么避免**:C.1 commit message 明确写"**ModbusDriver 必须 100% 兼容 ModbusMaster,68 测试无改动通过**",68/68 全过后才敢提交。

### 1.3 Qt 抽象类 + Q_OBJECT 必须显式构造(C.1)

**坑**:`Q_OBJECT` + `virtual ~X() = default;` → 编译器不生成默认构造,`DriverFactory::create("modbus", parent)` 编译不过。

**教训**:Qt 抽象类(Q_OBJECT + 纯虚函数)三件套 = 默认构造 + QObject* parent 构造 + 派生类构造。

```cpp
class IPollDriver : public QObject {
    Q_OBJECT
public:
    IPollDriver() = default;                          // ← 必须
    explicit IPollDriver(QObject* parent) : QObject(parent) {}   // ← 必须
    virtual ~IPollDriver() = default;
};
```

### 1.4 moc 需要 .cpp 文件(C.1)

**坑**:`IPollDriver` 是 abstract,所有方法纯虚,没有 .cpp → msvc 链接器找不到 `staticMetaObject`。

**教训**:Qt 抽象类也得配一个空 .cpp,只为触发 moc + 链接符号。

```cpp
// IPollDriver.cpp(空)
#include "drivers/IPollDriver.h"
// 故意留空 — include 头让 moc 看到 Q_OBJECT 就行
```

### 1.5 跨协议切换 = 重建(C.4 锁定)

**坑**:Modbus 地址 0x0002 在 S7 没意义,允许热切会崩。

**教训**:跨协议数据要明确"协议不变性",提前在文档/UX 锁死。

**怎么避免**:C.4 UX 规则锁定 — **不允许跨协议切工程**,弹错误"协议不兼容,请创建新工程"。

### 1.6 抽象层测试必须用 Mock(B4/B5/C.1)

**坑**:B4 只测了真实 Modbus,没测"按钮 enabled 跟协议无关" → updateButtons 覆盖时 Wqian 亲自验才发现。

**教训**:抽象层接口测试必须用 Mock 实现,不能只测真实实现。

**怎么避免**:C.1 加 `MockDriver` 类(完全脱离 Modbus),验证 PollScheduler 配它能跑 → 真协议无关。

## 2. 工作流教训(4 条)

### 2.1 vcxproj 必须同步(B4/C0/C1 都漏过)

**坑**:CMake 用 `GLOB_RECURSE` 自动捡新文件,但 VS 用的 vcxproj 是显式列表 — **不补会 LNK2019**。

**教训**:加新 .cpp/.h 第一件事同步 vcxproj + filters。**这是现状.md 第 5 节 #3 号约定**,忘了就写钉钉到 docs。

**怎么避免**:每个新里程碑 commit 都包含 1 条 `chore(vcxproj)` commit。

### 2.2 测试目录要凑齐传递依赖(C.0/C.1)

**坑**:加 `tst_ProjectSchema` 时,只加 Project.cpp 进 HMI_CORE_SOURCES,但 Project 链接到 ActionManager / ThresholdAlarmChecker / TcpClient 等。**每个测试都要把整条依赖链加进去**。

**教训**:tests 是独立编译,要从主程序"复制一份精简依赖"。

**怎么避免**:加新测试 → 看 cpp include 链 → 把所有间接依赖加进 HMI_CORE_SOURCES。

### 2.3 Qt 模块依赖跨域(C.0/C.1)

**坑**:`Project.cpp` 间接 include `QTcpSocket`(Network 模块)+ `QModbusDataUnit`(SerialBus 模块),测试 CMakeLists 没链 → 编译失败。

**教训**:tests CMakeLists `find_package(Qt6 ... COMPONENTS ...)` 要列出**所有**被 HMI_CORE_SOURCES 间接 include 的模块。

**怎么避免**:加新依赖时,grep "include <Qt" 列模块清单,逐个加进 COMPONENTS。

### 2.4 tests CMakeLists 的 components 列表是"用到就要加"

**坑**:C.1 加了 `Qt6::Network`(C.0 也有),但漏 `Qt6::SerialBus` → PollScheduler 引用的 QModbusDataUnit 找不到。

**教训**:Qt modules 是隐式的,include 就依赖,不能赌 cmake 自动加。

## 3. AI 协作 / 用户研究教训(4 条)

### 3.1 Wqian 亲自验视觉发现真 bug(B4)

**坑**:B4 单测覆盖了"权限 → setEnabled",但 hmi.cpp 里 `updateButtons()` 又调一次 setEnabled(覆盖权限)。**单测覆盖 != 真实集成覆盖**。

**教训**:关键功能必须人工验,不能 100% 信单测。

**怎么避免**:每个功能 commit 后,主动让 Wqian 启动看视觉(or 写 e2e 用例,见 3.3)。

### 3.2 Wqian 不会操作 UI(B3/B4/C.1)

**坑**:Wqian 自己说过"Wqian 不会操作 UI" → 自动触发 + 日志验证 是合适的绕过方案。

**教训**:跟非技术用户合作,设计测试方法要按用户能跑不能跑 — **自动 + 可观测**比"教用户操作"靠谱。

### 3.3 端到端测试 = headless 模拟真实流(C.0/B5)

**坑**:B5 audit.log 真实 GUI 验证需要 Wqian 启动 + 操作,他不方便。

**教训**:**端到端测试**可以 headless — 复制 main.cpp 的全部 connect + 真实调业务方法,等价覆盖真实 GUI 流程。

**怎么避免**:tst_AuditE2E 用 `wireUserManagerAudit(mgr)` 复制 main.cpp 的 audit 接线 + 调 mgr.addUser/login/etc → 6 类事件全在 audit 文件。

### 3.4 抽象类 + 抽象接口的"看起来相同"陷阱(C.1)

**坑**:IPollDriver.h 是抽象类,IPollDriver.cpp 是空文件(只为触发 moc) — 一开始忘了加 cpp → msvc 找不到 staticMetaObject。

**教训**:Qt 抽象类 ≠ Java abstract,Java 可以没有 .cpp,但 Qt 必须配(为 moc)。

## 4. 规划/沟通教训(4 条)

### 4.1 白话比喻让 Wqian 秒懂(B5/C.0/C.1)

**坑**:Wqian 多次问"这玩意干啥的"(B5/C.0/C.1 都问过)。

**教训**:复杂概念至少给 1 个现实类比,纯技术描述他听不懂。

**怎么避免**:
- B5 = 行车记录仪(事故复盘 2 秒查到谁改的)
- C.0 = 手机系统升级(老照片/微信记录都在)
- C.1 = 中文流外语(hmi 只会说"中文",要学"英语"S7 + "日语"EIP)

### 4.2 规划先写粗,Review 一轮再吸收(B/C 规划)

**坑**:阶段 C 详细规划 v1.0 写完后,Wqian 直接说"全改" — 一次性吸收 13 条建议出 v1.1。

**教训**:规划也要迭代,不追求一次完美。先写粗,Review 拿反馈,再优化。

**怎么避免**:每个大里程碑规划都按"v1.0 → Review → v1.1"两步走。

### 4.3 估时宁长不短(C 6-8 → 实际 10-13 周)

**坑**:路线图锁 C 6-8 周,实际 C 规划估 10-13 周 — 因为 3 个低估点:库调试 + 多 PLC 复杂度 + 合规咨询。

**教训**:T3 业余节奏,估时要悲观。

**怎么避免**:估时 + 20% buffer;每阶段加"为什么估时偏长"小节说明低估点。

### 4.4 用户打字错位("B5 是啥干啥的")

**坑**:Wqian 多次打字错位(B5 / C.0 / C.1 都问"这玩意是干啥"),但实际是想确认/理解。

**教训**:错位问题往往是真实困惑,**先讲明白再回它**;不要被错字带偏。
